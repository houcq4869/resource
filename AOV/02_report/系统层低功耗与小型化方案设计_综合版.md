## 0. 结论速览（TL;DR）

1. **问题本质**：AOV（周期唤醒抓 1 帧、抓完即睡的全时录像）要成立，系统层必须同时满足三件事——**睡得深（才省电）、时间不丢（才是证据）、醒了时间准（才可信）**；而 OpenHarmony L1 恰好在这三处"框架在、实现空"（内核 PM 三档默认同为 WFI、挂起服务是 sleep 模拟桩、NTP 链路断+无开机 RTC 校时、深睡时间无补偿）。这是系统层改造的根本动因。

2. **小型化**：按设备真实用途分层做减法（无屏→裁 UI 全家桶；单体→裁软总线族；只录像→裁显示/传感器框架/测试件），**零业务功能源码改动**（仅产品配置、组件构建元数据与少量上游缺陷修复）。实测：**内容体积 53.9→24.6MB（−54.4%）**，init 启动服务 **15→7**，构建目标 **−37%**，录像/AI/OTA 链路完整性验证通过。

3. **低功耗**：核心不是降频而是**分档休眠**（WFI→外设时钟门控→DDR self-refresh 逐级加深）。系统层补上五块地基：**休眠自动进入（OsIdleTask 覆写）→ 分档 PM 锁（K1）→ 设备链表（K3）→ 时间 offset（K2）→ 平台 SYSCTRL 分档钩子（B1）**，配业务层单帧循环骨架（aov_poc）与时间连续性闭环（RTC 校时+NTP+回写）。**双平台（SMP+UP）构建与符号级验证全部通过**。

4. **关键硬约束（构建实证）**：dv300 关闭 SMP 不可行——海思 MPP 预编译库按 SMP 编译引用 spinlock 外部符号，UP 链接失败；**从核 park 自研是 dv300 深睡的唯一路线**，单核机制验证转由 ev300（aries）承担（已完成对照构建，含 6 项基线修复）。

5. **三步走**：浅 AOV（树内闭环，✅ 代码全部落地，值守功耗建立 WFI 级基线）→ 标准 AOV（驱动监听/DVFS/WoW/MD 接入，对标值守 ≤80mW 保底/≤45mW 竞争）→ 深睡 AOV（DDR self-refresh，🔒 依赖海思 NDA，STR ≤40mW 保底/≤10mW 竞争）。

## 1. 设计目标与指标

### 1.1 总体目标

在 OH L1 小型系统（LiteOS-A）+ 海思 IPC 平台上，构建**系统级 AOV 低功耗框架**（功耗状态机、PM 锁治理、唤醒链路、时间连续性、计量体系），支撑 1fps 值守 + 事件全速录像，并使 OH L1 具备可复用的低功耗基础能力（分档锁/设备 PM 链表/时间补偿等均为通用机制，可回馈上游）。

### 1.2 分步指标

**口径纪律**：整板含 sensor、WiFi 保活、25℃、1fps 2MP；每项实测附测试条件（业界宣传值与整板实测差异可达 4~8 倍，如海思"80mW"营销口径 vs 开发板整板深睡实测 350mW）。

| 指标 | 第一步·浅 AOV | 第二步·标准 AOV | 第三步·深睡 AOV | 业界对标（调研实测/公开口径） |
|---|---|---|---|---|
| 值守功耗 | 建立基线实测（WFI 级收益） | **≤80mW 保底 / ≤45mW 竞争** | ≤45mW 稳定达成 | 海思 80mW（营销）/ 国科微单板 42mW / 君正 T33 26mW / RV1106 40mW |
| STR 深睡功耗 | — | — | **≤40mW 保底 / ≤10mW 竞争** | RV1126B 核心板 7mW / 宣称 1mW 级（裸片口径） |
| 唤醒延迟（唤醒源→首帧） | ≤1s | **≤500ms** | ≤250ms | 君正 TTFF<90ms / RV1106 250ms 抓图 |
| 事件切换（AI 命中→全速） | ≤2s | ≤1.5s | **≤1s** | RV1106 1s |
| 冷启动 TTFF | 分段打点建基线（✅ 插桩已落地） | ≤1.5s | **≤1s** | 全志 V853 700ms |
| 时间连续性 | 值守 24h 误差 ≤1s | + NTP 周期校时（✅ 链路已落地） | 深睡 7 天唤醒误差 ≤1s | — |
| 续航（9000mAh 折算） | — | ≥10 天 | **≥13 天** | 觅睿 V7 实测口径 13~15 天 |
| 存储占用 | ≤1GB/天 | **≤600MB/天** | 同左 | 觅睿全天 AOV 600MB vs 实时 15GB |

> 指标基线依据：业界 10 家芯片方案 + 14 款终端产品公开数据反推（详见《IPC AOV 业界方案调研报告》§4）。若第三步 NDA 不可得，方案上限锁定为"浅 AOV+WiFi 保活"组合，验收按保底列执行。

## 2. 现状与差距分析（凭什么要改系统层）

> 本节回答"为什么是系统层改造"——它是全部设计决策的依据。逐条证据（文件:行号）见《OH L1 低功耗现状与差距分析》。

### 2.1 内核 PM：「骨架完整、实现掏空」

| 存量（可复用） | 空缺（本方案补齐） |
|---|---|
| 4 档休眠枚举（NORMAL/LIGHT/DEEP/SHUTDOWN）、sysctrl/device 回调时序框架（含失败回滚）、带超时 PM 锁、唤醒竞态保护（LOS_PmWakeSet+二次检查）、动态 tick（空闲不空转） | 三档默认 handler 同为 `PRINTK+WFI`（档位无行为差异）；SHUTDOWN 档被禁用（handler=NULL）；PM 锁**全局一票否决**（无法表达"允 LIGHT 禁 DEEP"）；设备注册**单指针覆盖**；`OsIdleTask` WEAK 纯 WFI **无自动进入**；系统时间**无 offset 注入**（深睡掉电即时间丢失）；tickless 补偿空桩；无 DVFS/从核下线/arch 深睡汇编 |

对应改造点：B1/K4（自动进入+分档钩子）、K1（分档锁）、K3（设备链表）、K2（时间 offset）、K5（竞态参数启用）——**全部 ✅ 已落地**（§4.3）。

### 2.2 组件/驱动/平台层现状

- powermgr_lite：RunningLock→/proc/power→内核锁链路**真实贯通**（可复用）；但 small 形态挂起循环是 `sleep(10)` **模拟桩**（"using sleep to simulate suspend"原注释）→ **S1 ✅ 已修复**（真实挂起由内核 idle 钩子接管，服务循环改为策略槽位）。
- HDF PM：框架↔内核桥（devmgr_pm_reg.c 注册 DEVICE 节点）、驱动 listener API（IPowerEventListener 含 DOZE）、状态广播链、单测**意外齐备**——缺的只是外设驱动逐个挂接（⏳ 二步 B2）。
- 平台层：**零 SYSCTRL 注册**（deepSuspend 空置证实为"内核占位 WFI+平台零注册+服务假挂起"三重空置）→ **B1 ✅ 已落地**（pm_hi35xx.c 注册 early/late 计量 + normal/light/deep 分档钩子；deep 档第一阶段=WFI+时间补偿框架，真实电源域序列 🔒 待 NDA 资料填充）。
- 时间连续性**双断**：lwip sntp.c 未编入（LWIPNOAPPSFILES 排除）+ fixme.c `lwip_sntp_start` 空桩 + 全树无声明（C99 隐式声明必错）+ 无开机 RTC→系统时间同步 → **T4/T4b ✅ 已落地**（§4.5）。
- 唤醒源存量：RTC alarm 链路完整（irq37/32，驱动回调齐备）、GPIO 边沿中断完整、**hi3881 芯片级 PM+WoWLAN 完整（含 LiteOS 分支）**但未接系统 PM（⏳ 二步 B5）；UART 无 RX 唤醒。

### 2.3 差距清单（P0/P1/P2）

| 级 | 含义 | 代表项 | 处置状态 |
|---|---|---|---|
| P0 | 阻塞（不解决 AOV 不成立） | 假挂起桩(S1) / 无自动进入(K4) / 时间双断(T4) / 平台零注册(B1) / 深睡时间丢失(K2) | **✅ 第一步全部落地** |
| P1 | 影响达标 | 锁一票否决(K1✅) / 设备单指针(K3✅) / 驱动 listener(B2⏳) / WiFi WoW(B5⏳) / DVFS(B4⏳🔒) / 从核 park(🔒三步) | K1/K3/K5 机制先行✅；余项二步 |
| P2 | 工程质量 | 计量(T1✅+B1 挂起计量✅) / 唤醒源管理 API(S2⏳) / 真电池对接(S3⏳) / proc 权限(✅) | 逐步 |

### 2.4 平台硬约束（构建实证，影响路线选择）

1. **dv300 关 SMP 被否决**：关闭 `LOSCFG_KERNEL_SMP` 后内核链接失败——MPP 预编译库（base_mod_init/osal）与 dwc_usb3 按 SMP 编译，引用 out-of-line `LOS_SpinLock/Unlock/Init` 符号 1728+ 处；UP 构建下这些符号退化为头文件 inline → 未定义。**结论：dv300 保持 SMP，深睡需自研从核 park（第三步课题）；单核机制验证平台 = ev300**。
2. **预编译库-内核配置强耦合（双平台实证）**：ev300 的 libhi_osal.a 按旧代内核 ABI 引用 `g_percpu`（6.1 内核 UP 构建不定义）→ 已补 UP 兼容定义（最小 Percpu 结构，风险注记见 aries 报告）。**任何内核配置偏离默认，都需逐库验证链接闭包**。
3. **MPP 闭源边界**：liteos 侧 vi/venc/isp 全预编译 .a（内核态静态链入）；linux 侧 pmops 空桩。模块级电源策略只能走"deinit→电源域关断→re-init"路径（`SDK_exit()` 树内已存在、零调用者，B7 ⏳ 三步前置，稳定性需 PoC 专项）。
4. **uboot 预编译**（无源码）：冷启动 TTFF 的 uboot 段树内不可优化，预算中按实测值锁定。

## 3. 小型化方案：三工作期 + 三层裁剪

### 3.1 三工作期业务模型（裁剪与功耗设计的共同锚点）

| 工作期 | 业务 | 功耗量级 | 软件需求 | 对应内核档 |
|---|---|---|---|---|
| **值守期**（时间占比 >95%） | 周期唤醒抓 1 帧→检测→攒批落盘→回睡 | 目标 ≤80mW（保底） | 值守最小集（§3.2） | LIGHT（深睡期 DEEP） |
| **事件期** | AI 命中切 15~30fps 全速录像+抓拍+告警上传 | 1~3W | 值守集+JPEGE+大 VB 池+推流 | NORMAL（持锁） |
| **维护期** | 联网预览/OTA/配置下发 | Active 级 | 事件集+WiFi 全速+验签（huks/appverify） | NORMAL（持锁） |

**裁剪总原则**：值守期最小集常驻，事件期能力延迟加载，维护期能力按需拉起，无屏形态 UI 全家桶直接裁剪。

### 3.2 值守期最小必需集（裁剪锚点）

采集编码链（MIPI→VI→ISP→VENC/RC）· 检测链（libmd/IVE/NNIE 三选一，768×448 子流）· 存储链（FATFS+MMC/SD+1MB 攒批 fsync）· 时间链（RTC+开机校时+NTP）· 电源链（powermgr+内核 PM+计量）· OSD（RGN 时间戳，录像可回溯性必需）。

### 3.4 裁剪边界：阻塞项及原因（回答"为何不裁更多"）

### 3.5 内存布局重配（MMZ）⏳

DDR 512MB 现静态划 384MB 给 MMZ（`sdk_init.c:32-33`，内核 cmdline 固化）。方案：MMZ 降至 128~192MB + VB 池**双档位**（值守小池常驻/事件大池 `HI_MPI_VB` 动态申请释放），释放内存换 kernel 堆余量或缩小 DDR 有效容量以降自刷新保持域功耗。**状态：⏳ 待 T5 联调期实施**（值守管线 VB 需求需实测，本地构建无法验证运行时内存充足性）。

### 4.4 值守期单帧循环（接口约定 + 时序走查示例）

**目标态十步**：RTC 唤醒 → 时间校验 → sensor restart → SNAP 单帧 → 编码 → AI/MD → 攒批落盘 → sensor standby → 外设降电 → 设下一 alarm → 睡。唤醒窗口（步骤 3~9）预算 **≤100ms**（业界经验：每省 5ms 续航近翻倍）。

**当前实现走查**（aov_poc + K4/B1 联动，1s 值守周期实测口径待硬件）：

```
T+0ms     tick 中断唤醒 WFI（第一步周期唤醒；深睡期换 RTC alarm）→ 调度 aov_poc
T+1ms     AovSensorRestart：pfnRestart + 稳定延时（当前 100ms，Fast AE 收敛后收紧至 ~40ms）
T+~105ms  HI_MPI_SNAP_TriggerPipe → VI 单帧 → ISP（Run 线程常驻，二步切 RunOnce+曝光缓存）→ VENC
T+~120ms  GetStream(500ms 超时) → AovBatchAppend（1MB 攒批）
T+~121ms  AovMdCheck（桩；二步 HI_IVS_MD_Process）无事件
T+~121ms  AovSensorStandby：pfnStandby（sensor <10μW 级）
T+~122ms  满批才 write+fsync（1fps 低码率下约每小时 1 次 SD 唤醒——海思 KOL 同款攒批策略）
          任务 usleep(1s) → 无就绪任务 → idle：LOS_PmSuspend(0)
          → K1 分档锁检查（无锁/浅锁→放行或降级）→ early 计量点 → K3 设备链正序 suspend
          → lightSuspend(WFI) → 1s 后 tick 唤醒 → 设备链逆序 resume → late 计量
          → 每 64 周期串口输出 [AOV-PM] suspends/avg/max/locks
占空比：活跃 ~122ms/1000ms ≈ 12% → P_avg ≈ P_sleep + (P_active−P_sleep)×0.12
```

### 4.5 时间连续性方案（三保险 + 一预埋）

```
保险1 开机校时: HiRtcInit 尾部 → 读 RTC → civil↔epoch（自实现，年份<1970/>2099 拒校）→ settimeofday

预埋  深睡补偿: K2 offset（deep 钩子 RTC 差值 − CNTPCT 差值 → LOS_PmTimeOffsetAdd）
```

## 6. 关键设计决策与风险

### 6.1 关键决策（含理由）

1. **内核 offset（K2）必做而非应用层校时兜底**：`LOS_TickCountGet` 是软定时器/超时/日志时间戳的公共地基，深睡 CNTPCT 掉电后应用层无法自证时间——必须在 `OsGetCurrSchedTimeCycle` 统一注入。
2. **通道级启停优先于模块级 deinit**：闭源 MPP 整模块重启代价与正确性风险高（MMZ/ISP 重建），一期用 VI/VENC 通道级 + SNAP 单帧；模块级 deinit 仅深睡前执行（B7，PoC 专项先行）。
3. **从核 park 是 dv300 深睡唯一路线**（关 SMP 被预编译库链接实证否决，§2.4）；机制验证与深睡首证放 ev300 单核。
4. **K1/K3/K5 机制先行于功耗数据**：纯内核机制、不依赖硬件标定，提前落地可使第二步业务代码直接按分档锁语义编写；未调用的 Ex API 被 LTO 按需裁剪（调用即入镜像，零常驻成本）。
5. **裁剪顺序纪律**：external_deps 组件名耦合要求"先裁消费者、后裁被消费者"（device_auth 必须随 dsoftbus 同裁的实证教训）；对比构建必须 clean（staging 陈旧文件+depfile 对宏级头追踪不完整两个实证坑）。
6. **PoC 补丁纪律**：全部改动 git diff 归档（10 仓 3751 行+基线 commit 记录），工作树可一键回退；业务骨架不进 init 自启（bring-up 期手动拉起，避免与调试冲突）。

### 6.2 Top 风险

| 风险 | 等级 | 缓解 |
|---|---|---|

## 附录 C：术语表

| 术语 | 释义 |
|---|---|
| AOV | Always-On Video，全天候持续录像：周期唤醒低帧率抓拍+事件切全速，电池 IPC 的中国生态主导路线 |
| KOL | 海思 SDK 对 AOV 的命名（CV610 代），含 4 级休眠与 SINGLE 单帧采集模式 |
| TTFF | Time To First Frame，上电→首帧出图时间（快启指标，非开机时间） |
| STR / WFI | Suspend-to-RAM（DDR 自刷新保持）/ Wait For Interrupt（最浅休眠，时钟门控核心停转） |
| SYSCTRL / PM 锁 | LiteOS-A 内核 PM 的平台回调组（early/late/四档 suspend/resume）/ 阻止休眠的计数锁（本方案扩展为分档） |
| RunningLock | powermgr_lite 用户态锁服务（BACKGROUND 型→内核 PM 锁，链路已贯通） |
| MMZ / VB 池 | 海思媒体内存区（静态 384MB）/ 视频缓冲池（值守小池+事件大池双档位方案） |
| SNAP | MPP 单帧抓拍模式（SetPipeAttr/EnablePipe/TriggerPipe，AOV 单帧循环核心 API） |
| HDF / khdf / listener | OH 驱动框架 / 其 LiteOS 内核态形态 / 驱动电源回调注册接口（IPowerEventListener） |
| external_deps | GN 组件名依赖（要求部件在产品清单内，区别于直接路径依赖）——裁剪顺序约束来源 |
| whole-archive | 链接语义：archive 全部 object 强制载入（HDF/vendor 库区间），weak 覆写与无引用代码存活的前提 |
| DT_NEEDED | ELF 动态库依赖表（aov_poc 17 条全为 SONAME，运行时 /usr/lib 可解析） |
| jffs2 / vfat | aries（SPI NAND）与 taurus（SD/eMMC）的 rootfs 文件系统格式 |
