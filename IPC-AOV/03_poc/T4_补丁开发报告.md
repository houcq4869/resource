**时间链路全景**（阶段 4 §3.4 落地）：
```
开机: HiRtcInit → [AOV-TIME] boot sync ok（RTC→系统时间，录像时间轴起点）
联网: shell> ntpdate <server> → lwip_sntp_start → sntp_init（DNS/IP 均支持）
      → tcpip 上下文响应 → LwipSntpSetSystemTime → settimeofday
      → Hi35xxRtcWriteSysTime（回写 RTC，掉电重启不丢）→ [AOV-TIME] ntp writeback rtc ok
周期: sntp 内置 SNTP_UPDATE_DELAY=1h 自动重校（服务器名已静态持久化防悬垂指针）
```

## 2. 构建排障记录（重要架构认知修正）

### 2.1 `-Wcomment` 报错（轻）
文件头注释含 `porting/src/*.c`——块注释内 `/*` 序列触发 `-Werror,-Wcomment`。改写措辞修复。

### 2.2 duplicate symbol 与 lwip 构建路径真相（重要）

- **现象**：`duplicate symbol: lwip_sntp_start`，冲突双方 `lwip.sntp_port.o` vs `lwip.fixme.o`（均为 GN obj 路径）。
- **真相链**（修正了此前"enhancement/src 不参与编译"的误判）：
  1. **GN BUILD.gn 才是 lwip 的实际编译路径**（`obj/kernel/liteos_a/net/lwip-2.1/...` 对象命名证实；kernel_module GN target 真实编译 sources，含 enhancement/src 的 fixme.c/api_shell.c/dhcps.c）；Makefile 为并存的第二路径（本产品链接以 GN 产物为准）；
  2. 基线 `LWIP_SNTP` 未定义 → fixme.c 空桩块不编译 → 无冲突；我定义 `LWIP_SNTP=1` 后**空桩复活**与 sntp_port.c 撞车 → 删桩修复；
  3. **liblwip.a 不在 whole-archive 区间**（`-llwip` 于 los_config.mk:347 添加，早于 hdf_lite.mk:35 的 `--whole-archive`）→ 普通 archive 按需拉取：**未被引用的 object 不进镜像**——这解释了首轮 T4 构建"实现写在 fixme.c 却符号全灭"（fixme.o 无人引用未被拉出，链上 sntp.o 随之被 gc）；
  4. 本轮存活机制：`sntp_port.o ↔ sntp.o` 互引（sntp_init ↔ SNTP_SET_SYSTEM_TIME 宏）+ `SHELLCMD_ENTRY` 段注册根 → 整链拉出；`Hi35xxRtcWriteSysTime` weak 引用解析到 rtc 驱动强定义 ✓。
- **方法论沉淀**：小系统内核链接 = whole-archive（HDF/vendor 平台库，hdf_lite.mk:35~185 区间）+ 普通 archive（lwip 等）混合语义；**给"按需拉取"库新增能力必须自带存活根**（section 注册/被既有热点引用），否则静默消失；验证必须查 `sym.sorted`+`strings` 而非只看构建成功。

### 2.3 遗留一致性说明

## 5. 已知限制（PoC 口径）

1. `lwip_sntp_start` 返回值恒报首个服务器索引（不区分实际应答者，api_shell 打印的 server 名可能不准）——功能无影响；
2. 首次校时为同步阻塞等待（≤10s，shell/调用线程内）——产品侧自动校时应异步化（联网事件触发，T5/业务层）；
3. **开机自动 NTP 未做**（无网络就绪事件框架，small 系统 netmanager 缺失——阶段 2 已知）：PoC 用 shell 命令，产品化需业务层在 DHCP/关联成功后调用 `lwip_sntp_start`；
4. T4b 内核时间 offset（K2）未实施：LIGHT 档 CNTPCT 持续走时无需求；**DEEP 档（第三步）实施前必须补**（设计见阶段 4 §3.1-K2，落点 `los_sched_pri.h:82` + RTC 差值累加）；
5. RTC 掉电走时能力依赖板级（纽扣电池/超级电容），hispark 板实物确认列入硬件冒烟。

## 7. T4b 增补：内核时间 offset 机制（K2，DEEP 前置）——已实施并构建验证

> 原 §5.4 计划"第三步实施"，因机制可先行编译验证，提前至本轮完成（LIGHT 档下自动退化为零增量，无副作用）。

### 7.1 实现（4 文件）

| 文件 | 改动 |
|---|---|
| `kernel/liteos_a/kernel/extended/power/los_pm.c` | 新增 `g_osPmTimeOffsetCycle`（.bss 8B，符号实证）+ `LOS_PmTimeOffsetAdd/Get()` API |
| `kernel/liteos_a/kernel/include/los_pm.h` | 两 API 公开声明（供平台钩子调用） |
| `kernel/liteos_a/kernel/base/include/los_sched_pri.h` | `OsGetCurrSchedTimeCycle()` 叠加 offset（`#ifdef LOSCFG_KERNEL_PM` 守护，PM 关闭时零影响）→ LOS_TickCountGet/软定时器/gettimeofday 全链自动连续 |
| `pm_hi35xx.c` | 新增 `deepSuspend/deepResume` 钩子并注册：suspend 前记 CNTPCT+RTC epoch，resume 后 `offset += RTC差值×cycles_per_sec − CNTPCT差值`；**第一阶段 deepSuspend=WFI+计时框架**（CNTPCT 不停走 → offset 增量≈0，机制自校验），第三步插入真实电源域关断后自动生效 |
| `rtc_hi35xx.c` | 导出 `Hi35xxRtcReadEpoch()`（pm 钩子 weak 引用，复用 T4 civil↔epoch 转换） |

### 7.2 验证证据

- 构建零错误；`g_osPmTimeOffsetCycle` 入 .bss、`Hi35xxRtcReadEpoch`(0xdc) 入符号表、`[AOV-PM] deep resume: offset +...` 字符串入镜像（LOS_PmTimeOffsetAdd 被 LTO 内联进 HiPmDeepResume，属预期）；
- 硬件验证项（并入总冒烟单）：`echo deep > /proc/power/power_mode` 后跨休眠 `date`/软定时器精度；WFI 态 offset 增量应≈0（RTC 与 CNTPCT 一致性互验，顺带校验 OS_SYS_CLOCK=50MHz 与 CNTFRQ 实际值的一致性——若不一致此处会暴露，[TUNE] 项）。
