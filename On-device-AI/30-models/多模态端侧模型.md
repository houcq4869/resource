# 多模态端侧模型

> 2026-10-23 初稿。视觉/音频输入是端侧 AI 的核心场景（相机、语音），也是延迟问题的放大器。
> 相关：[[SLM设计演进]]、[[模型-硬件协同设计]]、[[异构调度与NPU利用]]

## 0. TL;DR

- VLM 的延迟瓶颈不在 LLM，在**视觉编码器**：高分辨率下编码时间成为 TTFT 的主导项（Apple FastVLM 实测）——"用 ViT 处理高分辨率图"在端侧是双重惩罚（编码慢 + 视觉 token 多拖慢 prefill）
- 端侧视觉编码器正在**去 ViT 化**：FastVLM 的卷积-Transformer 混合（比 ViT-L/14 小 8×、快 20×）、Gemma 3n 的 MobileNet-V5——卷积在前段下采样天然适合移动硬件
- 视觉 token 压缩的主流手段从"后处理剪枝"转向"架构内建"（MobileVLM 的 LDP 投影器 stride-2 卷积直接省 75% token）
- 语音侧成熟度更高：Whisper 类模型在 ANE 上已能近峰值利用率地跑流式转写

## 1. 问题结构：VLM 延迟的解剖

端侧 VLM（图像输入）的 TTFT = 视觉编码 + LLM prefill（视觉 token + 文本 token）：

```
分辨率 ↑ → 编码器延迟 ↑（二次方于 patch 数）
        → 视觉 token 数 ↑ → LLM prefill 线性变慢
```

EPFL 在 OnePlus 13R 的实测印证了分工错位（[arXiv:2507.08505](https://arxiv.org/pdf/2507.08505)）：

- llama.cpp 跑 LLaVA-7B：图像编码 ~2.4s + 图像解码 ~64s（表格数据）——**图像相关 prefill 占总延迟的 80%+**
- MLC-Imp 把视觉编码卸载到 GPU 后编码 18s 内完成、整机能效降 8 倍——但 GPU 饱和时出现过屏幕冻结
- 结论：**视觉管线（编码 + 融合 + 图像 token prefill）才是端侧 VLM 的主战场**，文本 decode 反而是次要矛盾

## 2. 视觉编码器：从 ViT 到混合架构

### 2.1 FastVLM（Apple，CVPR 2025，[arXiv:2412.13303](https://arxiv.org/html/2412.13303v2)）

- **FastViTHD**：卷积 stem + 3 个卷积阶段 + 2 个 Transformer 阶段，每阶段 patch embedding 空间减半——高分辨率图在进 Transformer 前已被卷积压缩
- 关键主张：**靠架构输出更少 token，而非事后 token 剪枝**——设计简单性本身是贡献
- 数据：比 ViT-L/14 小 ~8×、快 ~20×；同 0.5B LLM 下比 LLaVA-OneVision（1152 分辨率）**TTFT 快 85×** 且 SeedBench/MMMU/DocVQA 更好
- 0.5B 版本在 iPhone 16 Pro 上近实时（MLX + GPU 路径），已开源 iOS demo

### 2.2 MobileNet-V5（Gemma 3n 的选择）

Gemma 3n 用 **MobileNet-V5** 做视觉编码器（768×768）——移动端十年积累的纯卷积轻量网络回归主流 VLM（[模型文档](https://ai.google.dev/gemma/docs/gemma-3n)）。卷积网络在移动 NPU/DSP 上的算子支持成熟度远超 ViT。

### 2.3 投影器：token 压缩的另一个抓手

[MobileVLM（美团，2023）](https://arxiv.org/html/2312.16886)的 **LDP（轻量下采样投影器）**：

- depthwise 卷积（stride 2）把视觉 token 直接减 75%，<20M 参数、比视觉编码器快 81×
- 教训：单纯下采样掉 OCR 精度——需配合 PEG 类位置编码增强
- 整机实测：骁龙 888 CPU 21.5 tok/s、Jetson Orin 65.3 tok/s（2023 年数据，已有代差）

## 3. 代表模型全景

| 模型 | 模态 | 架构要点 | 端侧适配 |
|---|---|---|---|
| **Gemma 3n E2B/E4B** | 文本+图像+视频+音频 | MobileNet-V5 视觉 + USM 系音频编码器 + AltUp/LAuReL/SPARC/PLE（[HF 文档](https://github.com/huggingface/transformers/blob/main/docs/source/en/model_doc/gemma3n.md)） | 条件参数加载（纯文本任务不载视觉/音频权重）；140+ 语言 |
| **Apple 端侧 FM（2025）** | 文本+图像 | 图文输入，评测对标 InternVL-2.5-4B / Qwen2.5-VL-3B 且占优（[官方](https://machinelearning.apple.com/research/apple-foundation-models-2025-updates)） | OS 级集成，App 通过 Foundation Models 框架调用 |
| **FastVLM** | 图像 | FastViTHD + 简单投影 | iPhone 近实时；MLX 原生 |
| **MobileVLM / Imp-v1.5** | 图像 | CLIP ViT + LDP 投影 | 学术基准；EPFL 实测的常客 |
| **Whisper 系（语音）** | 音频 | encoder-decoder | ANE 近峰值利用率流式转写（[arXiv:2507.10860](https://arxiv.org/pdf/2507.10860)） |

## 4. 关键洞察

1. **"事后压缩"让位于"内建效率"**：token 剪枝/合并类方法（云端 VLM 常用）在端侧不如直接设计一个输出少 token 的编码器——与 [[KV cache与长上下文]] 的"架构层收益最干净"结论同构
2. **卷积在端侧复兴**：卷积段做早期下采样 + Transformer 段做语义聚合的混合结构，同时讨好内存带宽和 NPU 算子库
3. **音频走在图像前面**：语音输入的 token 经济学更宽松（1 秒语音 ≈ 数十 token），Whisper-on-ANE 证明"近峰值硬件利用率"在端侧可达——反衬 LLM decode 的 GEMV 困境（见 [[异构调度与NPU利用]]）
4. **条件参数加载是新维度**：Gemma 3n 允许"纯文本会话不加载视觉/音频权重"——**模态级的按需装载**与 MoE 的专家级按需装载是同一思想（见 [[MoE端侧化]]）
5. **评测短板**：端侧多模态模型普遍在 DocVQA/富文本图像类任务上吃分辨率亏——精度-延迟曲线的 Pareto 前沿仍是开放竞争
