# 量化技术

> 2026-10-23 初稿。端侧部署的第一道工序：把模型塞进有限的内存和带宽。
> 相关：[[推理框架横向对比]]、[[KV cache与长上下文]]、[[异构调度与NPU利用]]

## 0. TL;DR

- 量化对端侧是**双重刚需**：权重体积（8GB 内存手机放不下 3B FP16=6GB）+ decode 阶段带宽（GEMV 每步都要读全部权重，bit 数直接决定内存流量与速度）
- 方法论已收敛为**两段式统一框架**：预量化变换（rotation/scaling 平抑 outlier）+ 量化误差补偿（GPTQ 类二阶修正）
- 经验法则（1B–405B 系统评测）：**AWQ 优于 GPTQ；小模型 4-bit 脆弱、70B 级稳定；FP8 最稳；"量化后的大模型 > 更小的 FP16 模型"通常成立**
- **MXFP4 不是 INT4 的自动升级**：naive MXFP4 掉点 ~10%，需 MR-GPTQ 等格式定制方法才能逼近 NVFP4——FP4 时代的方法需要重写
- Apple 用"LoRA + 混合 2/4-bit（均 3.7bpw）"证明 2-bit 端侧可行，但依赖任务适配器兜底

## 1. 为什么端侧量化是刚需

| 约束 | 量化如何缓解 |
|---|---|
| 内存容量：8–12GB 手机要同时跑 OS + App + 模型 | 4-bit 让 3B 模型从 6GB 降到 ~1.5GB |
| 内存带宽：decode 是 GEMV，每 token 读全部权重 | bit 宽度直接除以内存流量 → **decode 加速比≈压缩比**（带宽受限时） |
| NPU 整数算力 | INT8/INT4 是 NPU 原生支持最好的格式 |
| 存储/下载 | 4-bit 模型可压进 App 分发预算（Gemma 3 1B 仅 529MB） |

## 2. 基础分类

- **PTQ（训练后量化）vs QAT（量化感知训练）**：PTQ 零训练成本、 minutes 级完成；QAT 精度更好但要训练管线。工业实践走向 QAT（Gemma 3 的 int4 QAT）甚至"量化感知蒸馏"（ExecuTorch 高通后端）
- **Weight-only vs Weight+Activation**：W4A16 最省事（激活仍 FP16）；W4A4/W4A8 才能吃到整数矩阵乘加速，但激活 outlier 是难点（→SmoothQuant）
- **量化粒度**：per-tensor < per-channel < per-group(32/64/128)。粒度越细、scale 开销越大、精度越好。MXFP4 的 group=32 是格式内建粒度
- **对称/非对称、均匀/非均匀**（KVQuant 的 sensitivity-weighted 非均匀编码是极致案例）

## 3. 方法演进主线

统一视角（[arXiv:2507.17417](https://arxiv.org/html/2507.17417v1)）把主流方法解耦为两步：

```
预量化变换（让分布更平、适合量化）
  ├── scaling（AWQ：激活感知的 per-channel 缩放，保护 ~1% 显著权重）
  ├── rotation（QuaRot/SpinQuant：Hadamard/正交旋转打散 outlier）
  └── SmoothQuant（把激活 outlier 迁移到权重侧，实现 W8A8）
量化误差补偿（抵消量化引入的误差）
  ├── GPTQ（OBS 血统：二阶 Hessian 信息逐列修正，one-shot）
  └── low-rank compensation（低秩残差补偿，与 GPTQ 可叠加）
```

关键实证结论：
- INT4 上 **optimized rotation + scaling + GPTQ(+low-rank) 是最优组合**（WikiText2 PPL 11.7 vs naive 的 923）
- **MXFP4 上规律反转**：scaling 类方法比 rotation 类更有效——INT4 时代的方法不能直接迁移到 FP4

## 4. 格式之争：INT4 vs FP4（Microscaling）

新一代硬件（NVIDIA Blackwell、AMD、gpt-oss 原生）推动 FP4 微缩放格式（[arXiv:2509.23202](https://arxiv.org/html/2509.23202v3)）：

| 格式 | 元素编码 | 组大小 | scale 类型 | 均摊 bits |
|---|---|---|---|---|
| INT4 (g128) | 整数 | 128+ | FP16 | ~4.06 |
| **MXFP4** | E2M1 浮点 | 32 | E8M0（2 的幂） | 4.25 |
| **NVFP4** | E2M1 浮点 | 16 | E4M3 | 4.5 |

实测（Llama-3.1-8B W4A4，平均恢复率）：

- **NVFP4 (96.1%) ≈ INT4+旋转 (96.1%) > MXFP4 (93.3% w/ MR-GPTQ, 87.8% naive)**
- MXFP4 的 E8M0 2 的幂 scale 引入较大量化误差；naive 情况下掉点 ~10%
- MR-GPTQ（块级 Hadamard + 格式定制 GPTQ）把 MXFP4 拉回到 NVFP4 的 1–2% 以内
- 结论：**FP4 不是免费午餐，需要格式感知的方法重写**；gpt-oss 原生 MXFP4 训练因此更稳（训练即量化，非 PTQ）

## 5. 端侧实践现状（各家的做法）

| 玩家 | 方案 | 备注 |
|---|---|---|
| **Apple** | 2-bit palletization，LoRA 适配器混合 2/4-bit，**均 3.7 bpw 达到 FP16 精度**；Talaria 工具逐算子选 bit 率；激活/嵌入也量化 | 任务特化 LoRA 兜住 2-bit 的质量损失——"通用 2-bit"仍未解决 |
| **Google (Gemma 3)** | QAT int4 通道级 + 运行时动态 int8 激活量化 | 529MB 分发体积，2585 tok/s prefill |
| **llama.cpp** | K-quants（Q4_K_M 等，超块结构）+ IQ 系列（重要性矩阵引导）+ KV cache 量化（q8_0/q4_0） | 格式即生态：GGUF 的量化目录是社区事实标准 |
| **MLC-LLM** | q4f16/q3f16 group quant，编译期烧进产物 | 权重 4-bit + 激活 FP16 的折中 |
| **ExecuTorch** | TorchAO int2/4/8；高通后端 QAT 蒸馏 | 量产路线重视可复现精度 |
| **OpenAI (gpt-oss-20b)** | 原生 MXFP4 | MoE + FP4 是"端侧友好"组合拳 |

## 6. 关键实证结论（1B–405B、13 数据集系统评测）

来自 [IJCAI 2025](https://www.ijcai.org/proceedings/2025/0902.pdf)（Llama-3.3 等指令模型、GPTQ/AWQ/SmoothQuant/FP8）：

1. **量化大模型 > 更小 FP16 模型**：多数基准成立，是端侧选型的重要依据
2. **FP8 一致最稳**，全尺寸全任务；AWQ 在 weight-only 中稳定优于 GPTQ
3. **小模型 4-bit 脆弱**：Llama-3.2-1B GPTQ-4bit 在 GSM8k 掉 25%；70B 级 4-bit 反而可能优于 8-bit
4. **掉点与任务难度不严格相关**——量化放大模型既有弱点（常识/逻辑/数学推理），Coding/STEM 掉点显著
5. IFEval（指令遵循）与 TruthfulQA（幻觉）是量化模型的普遍弱点 → 端侧 Agent 应用需重点回归测试

**对端侧的推论**：端侧恰恰运行 1–4B 小模型——正处在"4-bit 最脆弱"的区间。这解释了为什么 Apple 选择 2-bit+LoRA、Google 选择 QAT：**端侧不能只靠 PTQ**。

## 7. 开放问题

- [ ] 通用（非任务特化）2-bit：Apple 证明 3.7bpw+LoRA 可行，去掉 LoRA 兜底后？
- [ ] FP4 格式感知方法的统一框架（MR-GPTQ 之后）
- [ ] 量化 × MoE 的交互：路由器的量化敏感性、专家卸载（swap）时的粒度
- [ ] 量化与投机解码的耦合：draft 模型量化导致 acceptance 下降（见 [[投机解码与加速]]）
- [ ] 端侧评测缺口：现有结论多来自服务器 GPU；手机 NPU 上不同格式（INT8/INT16/FP16 混合）的真实能效曲线缺乏公开数据
