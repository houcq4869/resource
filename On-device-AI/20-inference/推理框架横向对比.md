# 推理框架横向对比

> 2026-10-23 初稿。对象：llama.cpp / MLC-LLM / MLX / ExecuTorch / LiteRT-LM(Google AI Edge) / MNN。
> 相关：[[异构调度与NPU利用]]、[[量化技术]]、[[端侧AI全景图]]

## 0. TL;DR

端侧推理框架存在**三条技术路线**，性能与可移植性呈跷跷板关系：

1. **手写内核路线**（llama.cpp、MLX）——每个硬件后端手工调优 kernel，性能天花板高，但多后端维护成本线性增长；
2. **编译器路线**（MLC-LLM/TVM、ExecuTorch）——从统一图 IR 自动生成各后端代码，可扩展性强，但工程链路重、单平台未必最快；
3. **系统服务路线**（Apple Foundation Models、Google AI Edge）——模型成为操作系统内置服务，开发者通过 API 调用而非管理模型文件。

没有一个框架在所有平台最快；**选型本质是"目标平台范围 × 团队工程能力"的函数**。

## 1. 三条技术路线详解

### 1.1 手写内核路线

代表：**llama.cpp**（ggml 张量库）、**MLX**（Metal Shading Language）。

- 内核逐后端手写：llama.cpp 为每种后端（Metal/CUDA/Vulkan/...）维护 C/C++ 内核；MLX 的快速路径是开源可读的 Metal 内核（矩阵乘、attention、量化权重内核）（[metalworking 书](https://metalworking.vercel.app/book/16-arrays-that-record/)）
- 优势：单后端可以压榨到硬件极限，迭代快（llama.cpp "代码即规范"，无 semv 语义负担）
- 代价：每新增一种加速器都要重写内核——这正是 **NPU 覆盖普遍缺失的结构性原因**（详见 [[异构调度与NPU利用]]）

### 1.2 编译器路线

代表：**MLC-LLM**（TVM/TensorIR）、**ExecuTorch**（torch.export + delegate）。

- 从单一图 IR 出发，编译期做算子融合、内存规划、目标代码生成
- ExecuTorch 的关键机制是 **delegate 分区**：图中被后端支持的区域下沉到加速器执行，不支持的算子回退到 portable CPU 内核——允许"部分加速"渐进落地（[官方文档](https://docs.pytorch.org/executorch/main/backends-overview.html)）
- 代价：编译链路长（MNN 的 QNN 离线模式就是典型：需 x86 host 交叉编译、按 SoC 生成离线产物）

### 1.3 系统服务路线

代表：Apple **Foundation Models 框架**（系统内置 ~3B 模型，Swift API + guided generation）、Google **AI Edge / LiteRT-LM**（.litertlm 格式 + RAG/Function Calling 库）。

- 模型内置于 OS，不占 App 体积、自动获得系统级优化（Apple 的 LoRA adapter 热切换、speculative decoding 由 OS daemon 完成）
- 意义：**框架层的竞争可能被操作系统抽空**——三方 App 直接消费系统能力，不再自己解决部署问题

## 2. 逐框架分析

### 2.1 llama.cpp

- **定位**：C/C++ 推理引擎，"本地 LLM"工具链的事实底座（Ollama、LM Studio 等都基于它）
- **格式**：GGUF（自有单文件格式，已成事实交换标准）
- **量化**：体系最全——K-quants（Q4_K_M/Q5_K_M/Q6_K/Q8_0）、IQ 系列（IQ2/3/4_XS/NL）、KV cache 量化（`--cache-type-k/v q8_0/q4_0`，需 `-fa`）
- **后端**：Metal / CUDA / ROCm / Vulkan / SYCL / CANN + CPU（AVX2/AVX512/NEON），矩阵最广
- **性能特征**：batch=1 单流 chat 负载优化（带宽受限），批量服务吞吐不及 vLLM 类引擎
- **短板**：NPU 基本无支持；无版本纪律，生产化需要自己锁 commit
- 来源：[Locara 框架综述笔记](https://locara.dev/docs/notes/llm-inference-frameworks)

### 2.2 MLC-LLM

- **定位**：基于 TVM Unity 的"一套引擎处处运行"通用部署引擎（CMU/Tianqi Chen 团队）
- **机制**：模型图 → TensorIR → 按目标生成二进制；量化（q3f16/q4f16/q4f32 group quant）在编译期烧进产物
- **API**：OpenAI 兼容接口覆盖 REST/Python/JS/iOS/Android，跨平台一致性强（[MLC 博客](https://blog.mlc.ai/2024/06/07/universal-LLM-deployment-engine-with-ML-compilation)）
- **实证表现**：EPFL 实测中，MLC-Imp 是唯一成功将 VLM 视觉+语言内核卸载到 Adreno GPU 的框架（CPU ≤120%、60°C、1.3W，对比纯 CPU 路线 10W/90°C）（[arXiv:2507.08505](https://arxiv.org/pdf/2507.08505)）
- **短板**：编译工具链重（Python pipeline、目标选择）；单一平台上通常不是最快

### 2.3 MLX（Apple）

- **定位**：Apple silicon 原生数组框架（NumPy 风格 API + autodiff），训练推理一体
- **三个架构决策**（官方设计说明 [issue #12](https://github.com/ml-explore/mlx/issues/12)）：
  1. **统一内存**——数组无 device 概念，CPU/GPU 操作同一缓冲区零拷贝，异构管线（CPU 量化 + GPU 解码）是常态
  2. **惰性求值**——操作只记录图，`mx.eval` 时统一调度进 command buffer，摊薄提交开销；每步只做一次 eval 是性能纪律
  3. **可组合函数变换**——`mx.grad/vmap/compile` 类 JAX
- **性能**：M 系列 sub-14B 模型比 llama.cpp 快 20–87%（[arXiv:2511.05502](https://arxiv.org/abs/2511.05502)）；M5 起通过 Metal 4 TensorOps 支持 GPU 神经加速器（[Apple ML Research](https://machinelearning.apple.com/research/exploring-llms-mlx-m5)）
- **生态位**：走 GPU 路线，与走 ANE 的 Core ML 互补；ExecuTorch 的 MLX delegate（实验性）也在将其纳入 PyTorch 部署链

### 2.4 ExecuTorch（Meta / PyTorch 官方）

- **定位**：PyTorch 原生端侧部署栈，`torch.export` → `.pte`，C++/Swift/Kotlin/JS 运行时
- **规模背书**：Instagram / WhatsApp / Messenger / Meta Quest / Ray-Ban Meta 生产在用（[GitHub](https://github.com/pytorch/executorch/)）
- **1.0（2025-10）**：XNNPACK+Arm Kleidi、Core ML、Qualcomm QNN、Arm Ethos-U、Vulkan 五个后端升 production；新增 Arm VGF、NXP、三星 Exynos、OpenVINO（[官方博客](https://pytorch.org/blog/introducing-executorch-1-0/)）
- **LLM 能力**（v1.5.x）：多方法导出、批量请求调度、off-graph KV cache 布局、Qwen3.5 MoE / Voxtral 等工作流；与 Hugging Face 合作打通导出
- **权衡**：每目标硬件单独导出 `.pte`（非一份文件走天下）；版本化部署合约换稳定

### 2.5 Google AI Edge / LiteRT-LM

- **演进**：TFLite → LiteRT；MediaPipe LLM Inference API 已进入**维护模式**，重心转向 **LiteRT-LM**（`.litertlm` 格式，Python/Kotlin/Swift SDK）（[官方文档](https://developers.google.com/edge/litert-lm/api_overview)）
- **代表数据**：Gemma 3 1B 仅 529MB，移动 GPU prefill 达 2585 tok/s（[官方博客](https://developers.googleblog.com/gemma-3-on-mobile-and-web-with-google-ai-edge/)）
- **工程优化亮点**（对其他框架有参考价值）：
  - QAT int4 通道级权重量化 + 运行时动态 int8 激活量化
  - KV cache 布局重排：减少多余 transpose/reshape，延迟 CPU +25% / GPU +20%
  - prefill/decode 两阶段 **GPU 权重共享**（LiteRT GPU delegate 首次可复用）
  - 优化后权重布局首次加载时落盘缓存
- **生态位**：Gemma 系列官方端侧路径，捆绑 RAG / Function Calling 库

### 2.6 MNN（阿里）

- **定位**：国产移动端推理引擎中 NPU 覆盖最全：QNN / CoreML / NNAPI / HiAI / RKNN 五种后端，且支持插件化动态加载（[MNN NPU 文档](https://github.com/alibaba/MNN/wiki/npu)）
- QNN 后端双模式：在线构图（运行时编译序列化）与离线构图（host 交叉编译产物，按 SOC ID + Hexagon arch 生成 `.bin`）——离线模式可省初始化时间，但暴露了 NPU 部署的工程复杂度
- 支持部分 LLM 的 NPU 推理加速
- （ncnn 腾讯系：移动端 CNN 推理见长，LLM 支持有限——待后续深入，此处不下结论）

## 3. 横向对比表

| 维度 | llama.cpp | MLC-LLM | MLX | ExecuTorch | LiteRT-LM | MNN |
|---|---|---|---|---|---|---|
| 出身 | 社区(ggerganov) | CMU/TVM | Apple | Meta/PyTorch | Google | 阿里 |
| 路线 | 手写内核 | 编译器 | 手写内核(Apple) | 编译器+delegate | 系统服务倾向 | 混合 |
| 模型格式 | GGUF | 编译产物 | safetensors 直读 | .pte | .litertlm | .mnn |
| 量化 | K/IQ 全系 | q3f16/q4f16 group | int2/4/8 (TorchAO via delegate) | TorchAO 系 | QAT int4+int8动态 | 自有 |
| NPU 支持 | ✗ | 有限 | ✗(走GPU) | ✓ delegate(产线级) | ✗(CPU/GPU) | ✓✓ 五后端 |
| 平台 | 最广 | 广 | Apple only | 广(移动→MCU) | Android/iOS/Web | 安卓系 |
| LLM 成熟度 | 最高 | 高 | 高(Apple) | 中→高 | 中(Gemma系) | 中 |
| 最适场景 | 快速验证、桌面 | 跨平台一致交付 | Mac/iPhone 深度优化 | PyTorch 生产链 | Gemma + 安卓 | 国产安卓全栈 |

## 4. 关键洞察

1. **性能-可移植性跷跷板**：llama.cpp 覆盖最广但单平台非最快；MLX 单平台最快但锁定 Apple；编译器路线试图两头兼顾，代价是工具链复杂度。
2. **GGUF 是事实交换标准**，而 .pte/.litertlm/.mnn 都是部署绑定格式——"模型文件可移植"与"硬件产物专用"的矛盾是端侧特有的（云端 ONNX 之争的重演，但碎片化更严重）。
3. **NPU 是所有通用框架的共同短板**：手写路线写不过来，编译器路线靠 delegate 分区渐进覆盖，MNN 靠人力硬扛五种后端。这是 [[异构调度与NPU利用]] 的主题。
4. **prefill/decode 两阶段分裂正在重塑框架设计**：资源需求完全不同（GEMM vs GEMV），催生 GPU 权重共享（LiteRT）、off-graph KV cache（ExecuTorch）、分阶段调度等专门机制。
5. **OS 级整合是潜在游戏规则改变者**：模型成为系统服务后，"选哪个推理框架"的问题对多数 App 开发者消失——Apple 已走出这一步，Google 用 LiteRT-LM + Gemma 跟进，安卓碎片化使后者覆盖有限。
