# 投机解码与加速

> 2026-10-23 初稿。唯一**不改变模型输出分布**的解码加速手段；与端侧 batch=1 场景天然契合。
> 相关：[[异构调度与NPU利用]]、[[KV cache与长上下文]]、[[量化技术]]

## 0. TL;DR

- 原理：小 draft 模型快速猜 k 个 token，大模型一次前向**并行验证**，概率性接受保证输出分布与原模型完全一致（无损）
- 方法演进已到第三代：独立 draft 模型 → Medusa 多头 → **EAGLE-3**（多层特征融合 + 训练时测试，加速 3–6.5×）→ MTP/DFlash 等嵌入式 draft
- **端侧是投机解码的最佳场景**：batch=1 延迟敏感、验证的并行度免费；NVIDIA TensorRT Edge-LLM 已内置 6 种 draft 方法
- **但端上落地有真实陷阱**：iPhone 17 Pro 上的 EAGLE-3 实验反而比基线**慢**（28.6 → 11–17 tok/s）——draft 质量衰减 + 验证内核开销，论文加速比 ≠ 设备实测
- 前沿方向：SLED 把投机解码重构为"端侧起草 + 边缘服务器验证"的端边协同范式

## 1. 原理与无损保证

自回归解码的瓶颈：每 token 一次前向，串行且无法并行。投机解码（Leviathan et al. 2023 等）：

```
1. draft 模型自回归快速生成 k 个候选 token（成本低）
2. target 模型一次前向并行验证 k 个位置
3. 从左到右接受最长正确前缀；某位置拒绝时，该位置的 target 分布
   直接作为下一个 token（拒绝采样修正）
```

**关键性质**：接受/拒绝规则保证最终输出与 target 模型独立生成的分布严格一致——加速不牺牲质量（区别于量化/剪枝）。

加速条件：`加速 ≈ 平均接受长度 × (target 单步成本 / (draft k 步成本 + target 验证一步成本))`。因此 draft 要**便宜且猜得准**，任务可预测性（代码 > 数学 > 开放生成）决定收益上限。

## 2. 方法演进

| 代际 | 方法 | 核心思想 | 加速比 |
|---|---|---|---|
| 一代 | Vanilla spec decoding | 独立小模型（同系列低参数版） | ~2× |
| 二代 | Medusa | target 上加多头，一次出多 token | ~2–3× |
| 二代 | EAGLE/EAGLE-2 | 复用 target 顶层特征做特征级外推 + 动态 draft 树 | ~3–4× |
| 三代 | **EAGLE-3** | 放弃特征预测改 token 预测；**多层特征融合**（低/中/高层）+ training-time test | **3–6.5×**（[arXiv:2503.01840](https://arxiv.org/html/2503.01840v2)） |
| 嵌入式 | MTP | draft 头内嵌在基座 checkpoint（Qwen3.5 等） | 规避独立 draft 的内存开销 |
| 边缘特化 | DFlash/DFlash2/DSpark/JetSpec | 块级 draft、选择器引导 | TensorRT Edge-LLM 内置 |

EAGLE-3 要点：

- 训练数据扩大对 EAGLE-1/2 无效（特征预测约束瓶颈），EAGLE-3 让 draft 充分享受数据 scaling
- 任务依赖明显：HumanEval（代码模板多）最高 6.5×、平均接受长度 7.5；数学推理次之
- vLLM 集成后吞吐提升至 2.5×（[Red Hat 实测](https://developers.redhat.com/articles/2025/07/01/fly-eagle3-fly-faster-inference-vllm-speculative-decoding)）

## 3. 端侧的特殊性

### 3.1 为什么端侧是理想场景

- **batch=1**：云端高并发下验证算力要跟多请求竞争（收益打折甚至负收益），端侧验证的并行度是"免费"的
- 延迟感知：TTFT/TPOT 直接对应体验
- NVIDIA 已在 [TensorRT Edge-LLM](https://nvidia.github.io/TensorRT-Edge-LLM/latest/user_guide/examples/speculative-decoding.html) 内置 MTP/EAGLE3/DFlash/DFlash2/DSpark/JetSpec 六种方法，含 draft 量化工具链（fp8/int4_awq/nvfp4/int8_sq）——**端侧投机解码已进入量产工具阶段**

### 3.2 端侧的三个陷阱

1. **内存税**：独立 draft 模型额外占内存（端侧最贵资源）→ EAGLE 单层头、MTP 内嵌是为此设计
2. **draft 量化掉 acceptance**：TensorRT 文档明确提示，draft 量化后接受率下降可能吃掉整体加速
3. **验证内核的现实开销**：[CoreML-LLM 项目在 iPhone 17 Pro 的实测](https://github.com/john-rocky/CoreML-LLM/blob/main/docs/EAGLE3_INTEGRATION_STATE.md)——EAGLE-3 部署后 11–17 tok/s，**反而低于基线 28.6 tok/s**：
   - 平均接受仅 ~2.0（Colab 上应为 3.05），滚动接受率 15 个 burst 内衰减到 0.30 后回退 T=1
   - 验证步（31.5ms）+ 提交步（33–36ms）的开销超过并行收益
   - 教训：**云端训练的 draft 头在端侧算子路径上未必有效；加速比必须以设备实测为准**

### 3.3 Apple 的做法

Foundation Models 框架把**投机解码与约束解码一起放进 OS daemon**（[WWDC25](https://developer.apple.com/videos/play/wwdc2025/286/)）：开发者不感知，系统统一调度——又一次体现"系统服务路线"把复杂度从开发者转移到 OS（见 [[推理框架横向对比]] §1.3）。

## 4. SLED：投机解码的范式外延

[SLED (ACM 2025)](https://doi.org/10.1145/3769102.3770608) 把 draft-verify 结构从"模型内"扩展到"设备间"：

- 轻量端侧设备（树莓派/Jetson）跑各自的 draft 模型起草
- 单台共享边缘服务器跑大 target 模型**批量验证**多设备请求
- 实测：系统吞吐 ×2.2、系统容量 ×2.8；断网时端侧仍保持 ≥5.24 tok/s（优雅降级）

意义：投机解码成为[[云端协同]]的新中间形态——比"全云"省成本、比"全端"质量高，验证本身就是一种"云监督"。与 Qualcomm Hybrid AI、端云协作学习（arXiv:2504.15300）形成呼应。

## 5. 关键洞察

1. **无损性是投机解码的护城河**：量化/剪枝都在赌质量换速度，它是唯一严格保分布的加速——对端侧"出厂即品质"的约束尤其珍贵
2. **加速比高度任务依赖**：代码 > 数学 > 开放生成；Agent 工作流（结构化输出、工具调用模板）恰是高可预测性场景，端侧 Agent + 投机解码是天然组合
3. **第三代方法的本质是"让 draft 享用 target 的表示"**：多层特征融合 + 数据 scaling，draft 不再是独立小模型而是 target 的"影子头"
4. **端上实测文化缺失**：论文加速比在 A100、SGLang 上取得；手机 SoC 的算子路径、热节流、ANE 限制都会改写结论——iPhone 17 Pro 案例是必读警示

## 6. 开放问题

- [ ] 接受率在线预测与动态 draft 长度（避免固定 k 的浪费）
- [ ] 热约束下的投机解码调度（draft 阶段的功耗预算）
- [ ] 投机解码 × KV 压缩的 cache 一致性（draft/verify 交替读写）
- [ ] 端侧 draft 头的本地训练/个性化（用户风格适配能否提升接受率）
- [ ] 结构化输出（guided generation）与投机解码的联合（Apple 已做系统级整合，开源侧空白）
