## 1. 语言与 UI：ArkTS、ArkUI、FA/Stage

### 1.1 ArkTS 是什么

ArkTS 是 OpenHarmony 应用的默认开发语言，在 TypeScript 生态上扩展，保持 TS 基本风格，但通过规范强化静态检查。[S6] 它不是“另一个完全不同语言”，而是**对 TS 的动态特性做减法、对声明式 UI/状态管理做加法**：

- 强制静态类型，禁止 `any` / `unknown`；[S7]
- 不支持 structural typing（结构化类型）；[S7]
- 禁止运行时改变对象布局（增删属性/方法、任意赋值）；[S7]
- 严格模式，不支持 `eval`、不支持用字符串动态创建函数；[S10]
- 扩展了声明式 UI、状态管理、并发等能力。[S6]

**边界**：ArkTS 兼容 TS/JS 生态，但“兼容”不等于任意 TS 代码零修改；`.ets` 在 API 10 以后按 ArkTS 规则做编译期检查。[S7]

### 1.2 ArkUI：声明式 + 类 Web，不是“新命令式”

ArkUI 官方列的是**两种开发范式**：

| 范式 | 说明 | 现状 |
|---|---|---|
| 基于 ArkTS 的声明式开发范式 | 用声明式语法描述 UI，渲染更新链路更短、内存更少 | 官方推荐，新应用首选 |
| 兼容 JS 的类 Web 开发范式 | 旧 JS/DOM 风格，保留兼容 | 与声明式共用 UI 后端引擎和语言运行时 |

来源：ArkUI 仓 README 明确写“两种开发范式，分别是基于 ArkTS 的声明式开发范式……和兼容 JS 的类 Web 开发范式”。[S8]

因此，**“命令式 ArkUI API”不是当前官方主推的新范式**；如果资料里说“ArkUI 命令式”，通常是指旧类 Web/DOM 风格，或指 Android/iOS 传统命令式 UI，不应与 ArkUI 声明式混为一谈。[S8]

**ArkUI-X** 是另一个项目：把 ArkUI 扩展到 OpenHarmony、HarmonyOS、Android、iOS，一套主代码多平台构建；它复用 OpenHarmony 的 ArkUI/ArkCompiler 仓，但有独立仓库与工具链（ACE Tools）。[S9]

### 1.3 FA 模型 vs Stage 模型

| 维度 | FA 模型（Feature Ability） | Stage 模型 |
|---|---|---|
| 起始版本 | API 7 | API 9 |
| 现状 | 已不再主推 | 当前主推、长期演进 |
| 应用组件 | PageAbility、ServiceAbility、DataAbility | UIAbility、ExtensionAbility |
| ArkTS 引擎 | 每个组件独享一个 ArkTS 引擎实例 | 多个组件共享同一个 ArkTS 引擎实例 |
| 对象共享 | 不支持进程内对象共享 | 支持进程内对象/状态共享 |
| 配置文件 | `config.json` | `app.json5` + `module.json5` |
| 开发方式 | 导出匿名对象、固定入口文件 | 面向对象、类接口、可派生 |

来源：OpenHarmony 应用模型文档明确“FA 从 API 7 开始支持，已经不再主推；Stage 从 API 9 开始，是目前主推且会长期演进的模型”。[S2]

Stage 模型的关键构件：

- **AbilityStage**：每个 Entry/Feature HAP 在运行期有一个实例，HAP 代码首次加载时创建。[S3]
- **UIAbility**：包含 UI 的应用组件，生命周期为 Create/Foreground/Background/Destroy，显示相关状态通过 WindowStage 事件暴露。[S3][S5]
- **WindowStage**：每个 UIAbility 实例绑定一个 WindowStage，作为应用进程内窗口管理器，持有主窗口，为 ArkUI 提供绘制区域。[S3]
- **Context**：UIAbility 和各类 ExtensionAbility 各有自己的 Context 派生类，提供运行期资源和能力。[S3]
- **ExtensionAbility**：面向特定场景的扩展组件，开发者不能直接继承基类，只能使用系统定义的派生类型。[S4]

### 1.4 ExtensionAbility 类型（节选）

| 类型 | 场景 | 三方可实现 | 独立沙箱 |
|---|---|---|---|
| FormExtensionAbility | 服务卡片 | 是 | 否 |
| WorkSchedulerExtensionAbility | 延时任务 | 是 | 否 |
| InputMethodExtensionAbility | 输入法 | 是 | 是 |
| AccessibilityExtensionAbility | 无障碍 | 是 | 否 |
| BackupExtensionAbility | 备份恢复 | 是 | 否 |
| EnterpriseAdminExtensionAbility | 企业设备管理 | 是 | 否 |
| ServiceExtensionAbility | 后台服务 | 否（系统） | 否 |
| DataShareExtensionAbility | 数据共享 | 否（系统） | 否 |

来源：ExtensionAbility 组件概述及类型表。[S4]

**注意**：Stage 模型下三方应用不能开发“自定义服务”，只能通过系统定义的 ExtensionAbility 派生类实现业务。[S3]

### 1.5 任务管理与多端协同的边界

- OpenHarmony 的“应用任务管理模型”文档标注为**仅对系统应用开放**。[S2]
- 多端协同当前**没有“多端协同任务管理”能力**，三方应用不能直接获取设备列表，只能由系统应用接入。[S53]
- 跨端迁移的触发也由系统应用完成，开发者只负责实现迁移数据的保存/恢复。[S52]

这三条是理解“分布式能力不是无限开放”的关键。

## 2. ArkCompiler：哪些开源、哪些是厂商工具

### 2.1 两大部分

ArkCompiler 由**编译工具链**和**运行时**两部分组成：

1. 编译工具链把 ArkTS/TS/JS 源码编译为 **abc（ArkCompiler Bytecode，方舟字节码）**；
2. 运行时直接执行 abc，实现语言语义。[S10]

运行时分为四个子系统：

| 子系统 | 内容 |
|---|---|
| Core Subsystem | File（承载字节码）、Tooling（Debugger）、Base（系统调用适配） |
| Execution Subsystem | 解释器、内联缓存（IC）、Profiler |
| Compiler Subsystem | Stub 编译器、IR 优化框架、AOT 编译器、代码生成器 |
| Runtime Subsystem | 对象分配/GC（CMS-GC、Partial-Compressing-GC）、DFX/Profiling、Actor abc 管理、标准库、NAPI |

来源：方舟运行时子系统 README。[S10]

### 2.2 执行模式：解释器、JIT、AOT、PGO

- **解释器**直接执行 abc；
- **JIT**：运行时仓有 `ecmascript/jit` 目录；JIT 依据运行时 profiling 生成机器码；
- **AOT**：`ark_aot_compiler` 在 Host 端把 abc 提前编译为目标机器码；[S12]
- **PGO**：`pgo_profiler` 是基于 Profile-Guided Optimization 的性能分析器；[S11]
- **GC**：CMS-GC、Partial-Compressing-GC；[S10]
- **并发**：Worker + TaskPool，TaskPool 支持优先级调度和工作线程自动扩缩容；[S10]
- **安全**：预编译为 abc，支持多重混淆；不支持 `eval` 和 sloppy 模式。[S10]

### 2.3 开源部分

以下仓在 OpenHarmony 组织下公开，构成“编译器/运行时/字节码工具”的开源主体：

| 仓 | 作用 | 证据 |
|---|---|---|
| `arkcompiler_ets_frontend` | 前端 `es2abc`，把 ArkTS/TS/JS 编译为 abc | “es2abc……将 JavaScript 文件转换为方舟字节码文件”[S13] |
| `arkcompiler_ets_runtime` | ArkTS 运行时，含解释器、JIT、PGO、GC、TaskPool | 目录含 `jit`、`pgo_profiler`、`taskpool`[S11] |
| `arkcompiler_runtime_core` | 语言无关运行时公共组件、abc 文件格式、ISA、汇编/反汇编、AOT/IR | `ark_disasm`、`ark_aot_compiler`[S12] |
| `arkcompiler_toolchain` | 调试调优工具 | ArkUI-X manifest 将其列为复用的 OpenHarmony 仓[S9] |

`arkcompiler_ets_frontend` 仓标注 **Apache License 2.0**。[S13] 其他仓的具体许可证需逐仓确认，不能笼统说“整个 OpenHarmony 都是 Apache 2.0”。

### 2.4 工具链：不是“只有 DevEco Studio”

- 编译/运行/反汇编/AOT 工具可以通过 OpenHarmony `build.sh` 构建，例如 `ark_disasm`、`ark_aot_compiler`；支持 Windows/Linux/macOS。[S12]
- `es2abc` 是命令行工具，可直接把源码编译为 abc。[S13]
- DevEco Studio 是华为提供的 IDE，**不在 OpenHarmony 代码仓**；命令行侧还有 `hvigorw`、`ohpm`、`hap-sign-tool` 等厂商工具。[S51]
- 在 OpenHarmony GitHub 组织下未检索到 `hvigor` / `ohpm` 的源码仓（检索日期 2026-11-02），因此更稳妥的表述是：**编译器/运行时/字节码工具开源；IDE 与构建编排工具按厂商工具链对待**。[S51]

### 2.5 关于 PIC

官方文档没有把 ArkCompiler AOT 产物描述为 **PIC（Position-Independent Code，位置无关代码）**。可确认的是：

- **abc 是平台无关的字节码**，设计目标包括屏蔽设备差异、支持跨设备分发；[S10]
- **AOT 产物是目标架构的机器码**，在 Host 端提前编译；[S12]
- 是否 PIC 取决于具体后端、重定位方式和加载器，文档层没有承诺。

因此，看到“ArkCompiler 支持 PIC”这类说法时应标为**待核实**，不能直接当官方事实。[S10][S12]

## 3. 应用打包、签名与分发

### 3.1 四种包：HAP / HAR / HSP / APP

| 包 | 全称 | 角色 | 关键点 |
|---|---|---|---|
| **HAP** | Harmony Ability Package | 应用安装/运行的基本单元 | 分 entry / feature；可独立安装运行 |
| **HAR** | Harmony Archive | 静态共享包 | 编译期复用；代码/资源跟随使用方编译；可发布 OHPM |
| **HSP** | Harmony Shared Package | 动态共享包 | 运行时复用；一个进程内只保留一份；随应用打包 |
| **APP** | Application Package / App Pack | 上架应用市场的基本单元 | 由 HAP/HSP + `pack.info` 组成；端侧安装/分发以 HAP/HSP 为单位 |

来源：应用程序包概述、Stage 模型包结构。[S14][S15]

### 3.2 HAP 内部结构

HAP 是编译打包产物，打包工具按 zip 方式组织，典型内容包括：

- `module.json`：编译后的模块配置（由 `module.json5` 生成）；
- `ets/*.abc`：ArkTS 源码编译后的方舟字节码；
- `resources.index`：资源索引；
- `resources/`：资源文件；
- `libs/*.so`：Native 库；
- `pack.info`：包属性描述（HAP/HSP 可带，APP 必带）。[S15][S17]

打包工具参数直接对应这些内容：`--json-path` 指向 `module.json`，`--ets-path` 指向 abc，`--index-path` 指向 `resources.index`，`--lib-path` 指向 libs，`--pack-info-path` 指向 `pack.info`。[S17]

### 3.3 Bundle 与 APP

- 一个应用的所有 `.hap` + `.hsp` 合称 **Bundle**，`bundleName` 是应用唯一标识。[S15]
- 上架时把 Bundle 打成 `.app`，同时生成 `pack.info`；`pack.info` 描述每个 HAP/HSP 的 bundleName、versionCode、module name/type/abilities 等。[S15]
- **APP 是上架/分发单元，不是端侧安装单元**；签名、云端分发、端侧安装都以 HAP/HSP 为单位。[S15]

### 3.4 AppSigning

OpenHarmony 要求**所有可执行代码签名**，只有签名过的应用/二进制工具才能安装、运行、调试。[S18]

签名链路：

1. 生成密钥对（推荐 ECC，不用 RSA）；
2. 生成应用签名证书；
3. 对 **Profile**（`p7b`）签名；
4. 对 HAP/HSP/APP 签名。[S19]

Profile（HarmonyAppProvision）关键字段：

- `bundle-name`：必须与 HAP 的 `bundleName` 一致，否则安装失败；
- `apl`：`normal` / `system_basic` / `system_core`；
- `app-distribution-type`：`app_gallery`、`enterprise`、`os_integration` 等；
- `permissions` / `acls`：受限权限与 ACL；
- `debug-info`：调试设备 UDID。[S20]

**证书注意**：OpenHarmony 代码仓预置了 `OpenHarmony.p12` 测试密钥库和对应证书，用于社区离线签名/验签；**商用版本必须替换**这些公钥证书和私钥。[S19][S21]

### 3.5 分发模型：OpenHarmony 与 AppGallery 的分界

- OpenHarmony 文档里的“应用市场”是抽象上架目标；它定义了 `app-distribution-type` 等元数据，但**不提供 AppGallery 这类商店实现**。[S15][S20]
- **AppGallery 是华为设备的官方应用分发平台**，AppGallery Connect / HMS Core 属于 HMS 生态。[S48][S49][S50]
- OpenHarmony 的系统应用清单是 Home/SystemUI/Settings 等，不含 AppGallery；具体设备带什么商店由发行版厂商决定。[S1][S48]

所以：

- 给 OpenHarmony 设备做应用：用 OpenHarmony SDK/API 开发，按发行版要求签名/分发；
- 给华为 HarmonyOS 设备做应用：用 HarmonyOS SDK，走 AppGallery；
- **不能把两者当成同一个商店/SDK**。[S1][S48][S49]

## 4. 分布式栈（OpenHarmony 开源部分）

### 4.1 总览

OpenHarmony 系统服务层的“系统基本能力子系统集”明确包括：**分布式软总线、分布式数据管理、分布式任务调度、公共基础库、多模输入、图形、安全、AI**。[S1]

| 能力 | 提供什么 | 关键仓 |
|---|---|---|
| 分布式软总线 DSoftBus | 近场设备发现、连接、组网、传输；屏蔽 WLAN/蓝牙等链路差异 | `communication_dsoftbus` |
| 分布式数据管理 | DDS、分布式 KV、分布式 RDB、分布式数据对象、分布式文件 | `distributeddatamgr_*` |
| 分布式任务调度 | 远程启动、远程迁移、远程绑定、远程 Call | `ability_dmsfwk` |
| 分布式硬件 | 硬件资源池、虚拟硬件、相机/屏幕/音频/输入跨设备调用 | `distributedhardware_*` |
| 设备认证 | 账号无关的设备发现/认证/组网 | `distributedhardware_device_manager`、`security_deviceauth` |

### 4.2 DSoftBus：发现、认证、组网、传输

DSoftBus 的目标是“近场设备间统一的分布式通信管理”，提供**不区分链路的设备发现、连接、组网和传输**。[S22]

代码结构直接对应四大能力：

```
core/
├── discovery        # 设备发现
├── authentication   # 认证
├── bus_center       # 组网/拓扑
├── connection       # 连接
└── transmission     # 传输
```

来源：DSoftBus README 目录结构。[S22]

关键约束：

- 组网设备必须在**同一局域网**，或距离相近的近场设备；
- 组网前必须先完成**设备绑定**（安全基础能力/deviceauth）；
- 数据传输完成后业务要主动关闭会话释放资源；
- 跨设备通信必须申请 `ohos.permission.DISTRIBUTED_DATASYNC` 和 `ohos.permission.DISTRIBUTED_SOFTBUS_CENTER`，权限类型为 **dangerous**。[S22]

传输能力支持**消息、字节、流、文件**。[S22]

### 4.3 分布式数据管理

#### 分布式数据服务 DDS

DDS 通过 **帐号 + 应用 + 数据库三元组**做数据隔离；在可信认证的设备间支持数据相互同步。[S23]

#### 分布式键值数据库 KV

- 单版本（SingleKVStore）：多个设备全局只保留一份数据，按时间最新保留；
- 设备协同（DeviceKVStore）：按设备维度区分数据，适合图库缩略图等场景。[S23][S24]

同步方式：

- **手动同步**：应用调用 `sync`，指定设备列表和模式：`PULL_ONLY` / `PUSH_ONLY` / `PUSH_PULL`；
- **自动同步**：在跨设备 Call 多端协同场景中，应用更新数据后由分布式数据库自动推送/拉取。[S24]

底层通信组件完成设备发现和认证后，数据管理服务在两台设备之间建立**加密数据传输通道**，再进行端端同步。[S24]

#### 分布式关系型数据库 RDB

- 把表设置为**分布式表**，即可在组网设备间同步；
- 多设备协同表模式：数据按设备 ID 隔离存储，默认模式；不能修改对端同步来的数据；
- 单版本表模式：API 23 起支持，数据直接写入本地表，可修改对端同步来的数据，需要配置 schema 指定同步列和解冲突列。[S25]

约束（节选）：每个应用最多同时打开 16 个关系型分布式数据库；单库最多 8 个数据变化回调；不支持复合键表。[S25]

#### 分布式数据对象

- 面向对象的内存数据管理框架；
- 每个对象创建一个分布式内存数据库，用 `sessionId` 标识；
- 只有**相同 bundleName** 的应用才能直接同步；
- 每个对象 100–150KB 内存，对象大小不超过 500KB；
- 通过软总线同步。[S26]

#### 分布式文件

应用沙箱的 `distributedfiles` 目录用于存放可跨设备直接访问的分布式文件；`.remote_share` 由系统管理，应用不要操作。[S37]

### 4.4 分布式任务调度 / 流转

`ability_dmsfwk`（原 `distributedschedule_dms_fwk`）提供：

- 远程启动元能力（跨设备拉起 UIAbility）；
- 远程迁移元能力（把 UIAbility 迁移到远端）；
- 远程绑定元能力；
- 远程 Call 调用（获取远端通用组件的 Caller 接口）。[S27]

官方概览进一步说明：分布式任务调度基于软总线、分布式数据管理、分布式 Profile，构建统一的服务管理（发现、同步、注册、调用），支持远程启动、远程调用、绑定/解绑、迁移，并结合设备能力/位置/状态选择合适设备。[S28]

#### 跨端迁移

- 应用层含义：A 端 UIAbility 迁移到 B 端，B 端继续任务，A 端可按需退出；
- 开发者实现 `onContinue()` 保存数据，对端用 `onCreate()` / `onNewWant()` 恢复；
- `module.json5` 中 `continuable: true`；
- 迁移触发由**系统应用**完成；
- `wantParam` 传输数据建议 <100KB。[S52]

#### 多端协同

- 支持跨设备启动 UIAbility / ServiceExtensionAbility、跨设备连接 ServiceExtensionAbility、跨设备 Call；
- 需要 `ohos.permission.DISTRIBUTED_DATASYNC`；
- **多端协同任务管理尚未具备，三方应用不能直接获取设备列表**。[S53]

### 4.5 分布式硬件

分布式硬件子系统把超级终端内各设备的硬件信息纳入**硬件资源池**，通过**驱动接口 HDI** 完成硬件虚拟化；服务层可以像使用本机硬件一样使用分布式硬件。[S29]

| 部件 | 提供什么 | 应用怎么用 |
|---|---|---|
| DeviceManager | 账号无关的设备发现、认证、组网、上下线状态 | 分布式设备管理接口 |
| 分布式硬件管理框架 | 硬件接入、查询、使能、资源管理、部件加载 | 不直接提供北向 API，由各硬件部件提供 |
| 分布式相机 | 跨设备使用对方 Camera；虚拟 Camera HDF | 通过相机框架，接口与本地相机一致 |
| 分布式屏幕 | 屏幕虚拟化、投屏/镜像/分屏 | 通过窗口/Display 接口 |
| 分布式音频 | 跨设备 Speaker 播音、Mic 录音 | 通过音频框架 |
| 分布式输入 | 跨设备键盘/鼠标/触摸板 | 通过多模输入框架 |

来源：分布式硬件子系统 README、各部件 README。[S29][S30][S31][S32][S33][S34]

**注意**：`分布式硬件子系统` 旧 README 的目录只列了 `device_manager`、`distributed_hardware_fwk`、`distributed_camera`、`distributed_screen`；但实际还有 `distributed_audio`、`distributed_input` 独立仓。说明文档存在版本滞后，做选型时要按目标分支核对仓。[S29][S32][S33]

## 5. 安全与 DFX

### 5.1 权限模型

OpenHarmony 的权限按授权方式分三类：

| 类型 | 授权时机 | 说明 |
|---|---|---|
| `system_grant` | 安装时自动授予 | 不涉及用户个人信息 |
| `user_grant` | 运行时弹窗请求 | 涉及用户个人信息；用户手动允许后生效 |
| `manual_settings` | 系统设置中手动授权 | API 21 起；不能弹窗，只能去设置里开 |

来源：应用权限管控概述。[S35]

APL（Ability Privilege Level）：

- 应用 APL：`normal`（默认）、`system_basic`、`system_core`；**应用 APL 不允许配置为 `system_core`**；
- 权限 APL：`normal`、`system_basic`、`system_core`；高等级权限默认只对高 APL 应用开放；
- **ACL**：低 APL 应用跨级申请高等级权限的特殊渠道，前提是该权限的“ACL 使能”为 true。[S35]

其他关键概念：

- **TokenID**：应用在设备内的唯一标识，权限管理服务用它管理 AccessToken（APP ID、子用户、分身、APL、授权状态）；
- **KernelPermission**：部分内核资源（如可执行匿名内存申请）也受权限保护；
- **安全访问机制**：系统 Picker + 安全控件，让应用按“用户选择的数据”临时访问，而不是直接拿整个权限。[S36]

### 5.2 应用沙箱

- 每个应用有独立的“应用沙箱目录”，只能看到自己的应用文件和少量系统文件；
- 路径经过权限隔离与挂载隔离，应用看到的是“沙箱路径”，不是真实物理路径；
- 文件加密等级 EL1–EL5：EL1 开机即可访问；EL2 首次认证后可访问（推荐默认）；EL4 锁屏不可访问；EL5 锁屏下满足条件可创建/读写。[S37]

### 5.3 SELinux 与 seccomp：应用 vs Native

**SELinux**：

- OpenHarmony 使用 SELinux 做强制访问控制（MAC），提供 `allow` / `neverallow` 规则；
- `sehap_contexts` 把应用关键信息映射到**应用进程标签**和**应用数据目录标签**；
- `appspawn` 在孵化应用进程时，根据 APL 设置 SELinux 标签（`HapDomainSetcontext`）；
- 支持 `debug_only` / `developer_only` 策略隔离宏，root 版和 user 版行为不同。[S38][S39][S40]

> 注意：`security_selinux_adapter` README 仍写“目前 SELinux 只支持 RK3568”，说明参考策略适配范围有限；具体产品是否启用、策略是否完整，要按发行版核对。[S38]

**seccomp**：

- 所有**应用进程**使能同一个 `app.seccomp.policy`，并受 `app.blocklist.seccomp.policy` 基线黑名单限制；
- 大部分**系统服务进程**使能同一个 `system.seccomp.policy`；
- init 孵化的 Native service 可以声明个性化策略；
- 返回值可以是 `LOG`（只记录）、`TRAP`（终止并交给 faultloggerd）、`KILL_PROCESS`、`KILL_THREAD`。[S41]

这就是“应用 vs Native”的主要差异：**应用统一策略 + 基线黑名单；Native 服务可按进程定制**。[S41]

### 5.4 代码签名与运行时完整性

- 所有可执行代码必须签名；只有签名过的应用/二进制工具能安装、运行、调试；[S18]
- 安装时包管理服务解析签名数据，用系统预置公钥证书验签，校验通过才允许安装；[S21]
- 代码签名组件还支持**本地代码签名**，例如 AOT 生成的 Native 代码；[S42]
- 商用版本必须替换 OpenHarmony 预置的测试证书/私钥。[S21]

### 5.5 DFX：HiLog / HiSysEvent / HiTrace

| 组件 | 作用 | 关键点 |
|---|---|---|
| **HiLog** | 流水日志 | 用户态 `hilogd` 常驻服务，环形缓冲区；`hilog` 命令行可过滤/落盘；支持隐私标识格式化、流控 |
| **HiSysEvent** | 系统事件埋点 | `HiSysEvent::Write(domain, eventName, type, keyValues...)`；支持上传云做质量度量 |
| **HiTrace** | 调用链跟踪 | 在跨设备/跨进程/跨线程通信中传递 `traceid`；Native TLS 存储；IPC/EventHandler 已支持 |
| **HiAppEvent** | 应用事件记录 | 应用事件记录接口/框架 |
| **FaultLoggerd** | 故障收集 | 应用故障日志采集/订阅 |
| **HiCollie** | 卡死检测 | 进程卡死看门狗 |
| **HiView** | 插件平台 | DFX 插件/事件分发 |

来源：DFX 子系统 README、HiLog/HiSysEvent/HiTrace README。[S43][S44][S45][S46]

## 6. 哪些**不属于** OpenHarmony

这是最容易混淆的部分，单独列出：

### 6.1 HarmonyOS / HarmonyOS NEXT 是华为商用发行版

- OpenHarmony 是**开放原子开源基金会**孵化并运营的开源项目；[S1]
- HarmonyOS 是华为的商用操作系统产品；HarmonyOS NEXT 是基于 OpenHarmony 打造的原生鸿蒙版本，但叠加了华为自有框架、SDK、分发和云服务。[S55][S48][S49]
- 不要把“OpenHarmony 开源”理解为“HarmonyOS 全部源码公开”；也不要把“HarmonyOS 应用”理解为“OpenHarmony 应用可以原样运行”。[S1][S55]

### 6.2 AppGallery / HMS Core / AGC 是华为商用层

| 名称 | 归属 | 作用 | 是否 OpenHarmony 组件 |
|---|---|---|---|
| **AppGallery** | 华为 | HUAWEI 设备的官方应用分发平台 | 否 |
| **AppGallery Connect (AGC)** | 华为 | 应用全生命周期平台：分发、运营、分析、云服务 | 否 |
| **HMS Core** | 华为 | 华为移动服务开放能力：Account、Push、IAP、Location、Map 等 | 否 |

来源：AppGallery 官方页面、HMS Core 文档、AGC 文档。[S48][S49][S50]

OpenHarmony 只提供端侧框架/接口；云账号、推送、支付、地图、应用商店运营等由厂商服务提供。OpenHarmony 的“帐号”子系统描述也是“对接**厂商云帐号应用**”，不是内置华为账号。[S1]

### 6.3 文档明确“未开源/打桩”的部分

`安全基础能力子系统` README 明确写了两条：

- **同帐号设备认证在本期不开源**（使用打桩实现支持上层联调）；
- **分布式应用权限管理在本期不开源**（使用打桩实现）。[S47]

这意味着：OpenHarmony 开源的是**账号无关的点对点设备认证**；同账号生态能力、分布式权限管理在开源版里不是完整实现。做产品选型时必须把这两条列为风险。[S47]

### 6.4 其他不属于/不应假定的部分

- **DevEco Studio IDE**：华为提供的 IDE，不在 OpenHarmony 代码仓；命令行 `hvigorw`/`ohpm`/`hap-sign-tool` 也是厂商工具链。[S51]
- **商用签名 CA / 应用商店证书体系**：OpenHarmony 预置测试证书，商用要替换。[S21]
- **应用商店审核、上架、运营、云测试**：属于厂商/商店能力，不是 OpenHarmony 系统组件。[S48][S50]
- **HarmonyOS 专有 Kit/云 API**：不能假定在 OpenHarmony 上可用；要逐项核对 API 是否属于 OpenHarmony 标准 API。[S1][S48]
