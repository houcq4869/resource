## 1. 构建栈：一个引擎，两条历史

### 1.1 当前 `build` 仓：GN + Ninja + hb（三系统通吃）

`build` 仓 README 开宗明义："编译构建子系统提供了一个基于Gn和ninja的编译构建框架"，流程是 `gn gen` → 生成 ninja → `ninja` 执行（[gitee build/README_zh.md](https://gitee.com/openharmony/build/raw/master/README_zh.md)，2026-11-02）。

关键点是 **`build.sh` 并不是独立构建系统**。根目录的 `build.sh` 来自 manifest 的 linkfile：

```xml
<!-- manifest/ohos/ohos.xml (master) -->
<project name="build" path="build" remote="gitcode" revision="master"
         groups="default,ohos:mini,ohos:small,ohos:standard,ohos:system,ohos:chipset">
  <linkfile dest="build.sh" src="build_scripts/build.sh"/>
  <linkfile dest=".gn"      src="core/gn/dotfile.gn"/>
  <linkfile dest="build.py" src="build_scripts/build.py"/>
</project>
```
（<https://raw.githubusercontent.com/openharmony/manifest/master/ohos/ohos.xml>，2026-11-02）

而 `build_scripts/build.py` 里只有一句核心：

```python
python_executable = get_python(python_dir)      # 找 prebuilts/python/.../python3
cmd = [python_executable, 'build/hb/main.py', 'build'] + args_list
```
（`build/build_scripts/build.py:79-85`，commit `961ba684` <https://github.com/openharmony/build/blob/961ba684a2c9a1feaa063cbe597ebf04642f297d/build_scripts/build.py#L79-L85>）

同一文件还保留了旧入口开关：

```bash

```
（`build/build_scripts/build.sh:188-197`）即 **默认新 hb，`--using_hb_new=false` 回落到旧 `entry.py`**。build 仓自己的 `AGENTS.md` 也这样写："`build.sh` 分发到 `build/hb/main.py build`（新 hb，默认）"（<https://github.com/openharmony/build/blob/961ba684/AGENTS.md>）。

## 2. `hb set / hb build / hb clean` 到底做什么

官方"编译构建指导"给出的机制（[subsys-build-all.md](https://raw.githubusercontent.com/openharmony/docs/master/zh-cn/device-dev/subsystems/subsys-build-all.md)，2026-11-02）：

- `hb clean`："清除out目录对应产品的编译产物，仅保留 args.gn、build.log"。

### 3.1 三层 Python

### 3.2 uv 的真实位置

`master` 的 `prebuilts_download.sh` 把依赖列表按 L0/L1 与标准系统分开：

```bash
# L0/L1 (mini/small systems) need no rust bindgen (libclang), no SBOM
# generation (networkx, packageurl, license-expression) ...
case "${BUILD_LEVEL}" in
  L0|L1) prebuilt_pip_packages=( idna urllib3 pyyaml requests prompt_toolkit==1.0.14 json5 psutil ) ;;
  *)     prebuilt_pip_packages=( ... "libclang==15.0.6.1" "uv==0.9.18" "blake3==1.0.8" ) ;;
esac
```
（`build/prebuilts_download.sh:271-311`，<https://raw.githubusercontent.com/openharmony/build/master/prebuilts_download.sh>）

三点结论：

1. **uv 是 6.1 之后才加的**：`OpenHarmony-6.1-Release` / `6.0-Release` 的同文件都 **没有** `uv==`（本次逐个 grep 验证）。
2. uv 只出现在 **pip 安装清单**里；在 `build` 仓全文检索 `\buv\b` **只有这一行命中**，`hb`、`build.sh`、SBOM 脚本都没有 `uv run/uv pip`。→ **不能声称"hb 需要 uv 环境"**。
3. mini/small（L0/L1）根本不需要 uv / libclang / SBOM 依赖，这也是"轻量系统编译环境更轻"的机制性解释。

### 3.3 hb 安装的真实坑（prompt_toolkit）

（<https://www.winter.xyz/python/59.html>；同类报告 <https://bbs.ai-thinker.com/forum.php?mod=viewthread&tid=46250>，均 2026-11-02 访问）

> "device … 芯片厂商适配目录，其中 config.gni 描述当前芯片使用的 arch，工具链…；vendor … 终端模组厂商适配目录，其中 config.json 描述需要集成的子系统列表"

目录规则 `device/{芯片厂商}/{芯片开发板}`（例 `device/MyDeviceCompany/MyBoard`）+ `vendor/{产品模组厂商}/{产品模组名称}`，`config.json` 中 `device_company` / `board` 必须与 device 二级/三级目录一致，`subsystem`/`component` 必须与 `build/lite/components/*.json` 匹配（否则构建前检查报错）。

真实 mini 产品：`vendor_hisilicon/hispark_pegasus/config.json`，`"type": "mini"`, `"device_build_path": "device/board/hisilicon/hispark_pegasus"`, `kernel_type: liteos_m`, `kernel_is_prebuilt: true`。

### 4.4 文档自相矛盾（必须在笔记里标出来）

- `subsys-build-chip_solution.md` 正文写 **"源码路径规则为：device/{开发板}/{芯片解决方案厂商}"**，但紧接着的目录树是 `device/board/company/hispark_aries`，示例命令是 `mkdir -p device/board/realtek/rtl8720`。**正文路径写反了，以目录树/示例/实际仓为准：`device/board/{company}/{board}`**。
- `porting-smallchip-prepare-building.md` 仍用 **`device/hisilicon/hispark_taurus`**（3.1 之前的布局），与现行 `device/board/...` + `device/soc/...` 不一致。写笔记时应标注"3.1 前 / 3.1 后"。

## 5. 构建产物：按系统类型分

### 5.1 标准系统：`out/{device_name}/packages/phone/images/`

镜像清单有权威表（`subsys-boot-deviceboot.md`）：

| 镜像 | 挂载点 | 说明 |
|---|---|---|
| `boot.img` | NA | 内核和 ramdisk，"bootloader加载的第一个镜像" |
| `system.img` | /system | "系统组件镜像，存放与芯片方案无关的平台业务" |
| `vendor.img` | /vendor | "芯片组件镜像，存放芯片相关的硬件抽象服务" |
| `updater.img` | / | "升级组件镜像…正常启动时不加载" |
| `userdata.img` | /data | 可写用户数据 |

`build/ohos/images/BUILD.gn` 的 `make_images` 还会产：`eng_system.img`、`eng_chipset.img`、`sys_prod.img`、`chip_prod.img`、`updater_ramdisk.img`，`enable_ramdisk` 时加 `ramdisk.img`，`device_name == "rk3568"` 时额外 `chip_ckm.img`；`chip_product_list` 非空时按子产品输出 `images/<product>/chip_prod.img`（`subsys-build-reference.md` "定制打包chip_prod镜像"）。

板级另出 `uImage`（内核）与 `uboot`（bootloader）到同一 images 目录（`standard-system-porting-guide.md:122-123`）。

### 5.2 小型系统（Hi3516 为范本）

`quickstart-pkg-3516-burn.md` 的分区表直接给出文件名：

- LiteOS-A：`u-boot-hi3516dv300.bin` + **`OHOS_Image.bin`** + **`rootfs_vfat.img`** + **`userfs_vfat.img`**
- Linux：`u-boot-hi3516dv300.bin` + **`uImage_hi3516dv300_smp`** + **`rootfs_ext4.img`** + **`userfs_ext4.img`** + **`userdata_ext4.img`**

`OHOS_Image` 的生成机制（mini 移植文档）：`executable("OHOS_Image.elf")` → `objcopy -O binary OHOS_Image.elf OHOS_Image.bin`（`porting-minichip-kernel.md`）。

### 5.3 轻量系统（Hi3861）

烧写只需两个文件：**`Hi3861_wifiiot_app_burn.bin`**、**`Hi3861_loader_signed.bin`**（`quickstart-pkg-3861-burn.md`）；产物目录 `out/hispark_pegasus/wifiiot_hispark_pegasus`（`quickstart-pkg-3861-build.md`）。

## 6. 烧录与 IDE

### 6.1 DevEco Device Tool（Windows+Ubuntu 混合）

- **最后版本 4.0.0.400**（`devicetool-windows-tool-4.0.0.400.zip` / `devicetool-linux-tool-4.0.0.400.zip`），官网下载页至今只列 4.0 Release（<https://device.harmonyos.com/cn/develop/ide/>，2026-11-02）。历史页只到 4.0 Beta1（2023-08-01）。**没找到 2025-2026 的新版本，也没有官方 EOL 公告**——只能写"事实冻结在 4.0"。
- 架构：Windows 侧编辑/烧录/调试，Ubuntu 侧编译；"DevEco Device Tool通过Remote远程模式，将Ubuntu环境下编译生成的待烧录程序文件拷贝至Windows目录下，然后通过Windows的烧录工具将程序文件烧录至开发板"（`quickstart-ide-3861-burn.md`）。
- 烧录协议按板不同（同一 `Upload` 按钮，`upload_protocol` 不同）：

| 板 | 协议 | 说明 |
|---|---|---|
| Hi3861 | `hiburn-serial` | 选 COM 口 + 15s 内按 RST |
| Hi3516 | `hiburn-usb` | 默认同时烧 fastboot/kernel/rootfs/userfs，需手配起始地址与长度 |
| RK3568 | `upgrade` | 用 `upload_partitions_profile` 生成分区表 |

- 调试能力：官方渠道称"支持 GDB、LLDB 调试，提供变量监控、内存地址查看、寄存器查看和反汇编查看"（<https://devicepartner.huawei.com/cn/tools-platforms>）；4.0 新增 **RTT 调试**（"打通Windows环境和调试设备之间的RTT通道"）。文档 quick-start 只覆盖 Build/Upload/Monitor，**没有独立的 Debug 章节**。

### 6.2 命令行烧录（不装 IDE）

- Hi3861：**HiBurn**（勾 Select all + Auto burn，Connect 后按 Reset）
- Hi3516：**HiTool**（USB + 烧写 eMMC，导入自写 `Partition_Info` xml，按住 Update 键插拔 USB）
- RK3568：**RKDevTool** + `DriverAssitant_v5.1.1`
- 标准系统还可用 **`hdc flash`**：需先 `hdc shell write_updater boot_flash; hdc shell reboot updater` 进升级模式，然后 `hdc flash <image name> <image path>`，例如 `hdc flash updater_ramdisk updater_ramdisk.img`（`subsys-toolchain-hdc-guide.md`）

### 6.3 设备开发快速入门"标准动作"（hi3861 为范本）

`quickstart-overview.md` 定义三系统与三板对应：Hi3861→轻量(128KiB)、Hi3516DV300→小型(1MiB)、RK3568→标准(128MiB)；两条路径（IDE / 命令行），流程均为：

**装环境 → 取源码 → 写 Hello World → 编译 → 烧录 → 运行/联网**

命令行版 hi3861 具体命令（`quickstart-pkg-3861-build.md`）：

```
hb set          # 选 . → hisilicon → wifiiot_hispark_pegasus
hb build -f     # 全量；hb build 增量；hb build -T <target> 单目标
```
环境侧额外要求 `SCons 3.0.4+`、`setuptools/kconfiglib/pycryptodome/six/ecdsa`、**`gcc_riscv32`**（`quickstart-pkg-3861-tool.md`）。

### 7.1 工具链从哪来

`build/prebuilts_config.json` 是唯一权威清单（`tool_list`）：`llvm`、`gn`、`ninja`、`python`、`node`、`hc-gen`、`rustc`、`hvigor`、`packing_tool`、`libcxx-ndk`、`taihe`、`sdk`、`cangjie`、`ark_js_prebuilts`、`AGPBinaryCompile`、`hpm`、`npm_install`、`node_modules_copy`、`OpenHarmonyApplication.pem`。

具体版本（master，2026-11-02）：

| 工具 | 版本 / 时间 |
|---|---|
| clang/llvm | `15.0.4-115b62` / **`...-20250811.tar.gz`** |
| gn | `20250903`（x86_64），`20240530`（aarch64） |
| ninja | `1.12.0` |
| python | `3.11.4`（`..._20250807`） |

### 7.2 许可

- 仓本身：Apache-2.0（`build/LICENSE`、`hb/setup.py: license='Apache 2.0'`）。
- **编译工具不进 NOTICE**：官方明确"只收集打包到镜像里面的模块对应的License；不打包的都不收集，比如构建过程使用的工具（如clang、python、ninja等）"（`subsys-build-reference.md`）。→ 用 prebuilts 不需要额外签署工具许可，义务落在镜像内组件的 `NOTICE.txt` 聚合。

- 厂商二进制（如 Hi3516 uboot prebuilts、Hi3861 SDK）遵循各自目录 LICENSE（`device_board_hisilicon/hispark_taurus/README_zh.md`："参见对应目录的LICENSE文件及代码声明"）。

## 8. 2025–2026 的构建体系演进（逐条给证据）

1. **托管平台迁到 GitCode**（影响所有构建脚本里的下载地址）
   - manifest：`<remote fetch="https://gitcode.com/openharmony" name="gitcode"/>` + `<default remote="gitcode">`（2026 版权头）。
   - 6.0 文档改口："开源代码仓库地址：https://gitcode.com/openharmony"、"repo init -u https://gitcode.com/openharmony/manifest.git"（`OpenHarmony-6.0-Release/zh-cn/device-dev/get-code/sourcecode-acquire.md`）。
   - 但对 `gitee.com/openharmony/...` 的引用在文档里仍大量残留（`quickstart-appendix-compiledform.md` 的 config.json 链接已换成 gitcode）。

2. **工具链升级（2025 年内）**：clang 15.0.4-115b62（2025-08-11）、gn 20250903、python 3.11.4（2025-08-07）、prebuilts config pruning（build 仓 2026-09-24 提交）。

3. **新增 SBOM 生成**（6.0 引入，2025-09-04 合入 `!5889 生成SBOM`）
   - 用法：`./build.sh --product-name {product_name} --sbom=true`
   - 产物：`out/{product_name}/sbom/sbom_meta_date.json` + `spdx.json`（SPDX 2.3）
   - hb 侧新增 `--sbom` 参数（`hb/resources/args/default/buildargs.json`，`resolve_sbom` 在 `postTargetGenerate` 阶段起线程跑 `build/ohos/sbom/generate_sbom.py`）
   - 这解释了为什么标准系统要多装 `networkx / packageurl-python / license-expression / libclang`。

4. **构建环境按 `BUILD_LEVEL` 分层**（L0/L1 精简依赖），并在 master 追加 `uv==0.9.18`、`blake3==1.0.8`（6.1 无此二项）。

5. **`build_lite` 彻底退场**（2023 冻结、manifest 移除、`build/lite/hb` 删除），文档"相关仓"里仍链着它 → 是**文档债**，不是现状。

6. **6.0/6.1 Release Notes 不记录构建变更**：`OpenHarmony-v6.0-release.md`（32KB）与 `v6.1-release.md`（26KB）grep `编译构建|构建|hb|SBOM` **零命中**。→ 判断构建演进只能看仓的提交与脚本，不能靠 release notes。
