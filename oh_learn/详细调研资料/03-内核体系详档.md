## 0. 先给结论（TL;DR）

- OpenHarmony 是**多内核**架构：LiteOS-M（轻量/MCU）、LiteOS-A（小型/Cortex-A）、Linux LTS（小型+标准），三者通过 **KAL** 向上给统一接口，驱动侧通过 **HDF + OSAL + khdf 适配层**跨内核复用。
- Linux 基线是 **LTS 4.19.y / 5.10.y / 6.6.y** 三条，采用「**Common Kernel 基线 + 厂商板级补丁**」的 patch-set 策略，默认构建已是 **linux-6.6**；4.19 仓已进入**仅维护**状态。
- 官方仓库实际存在 **11 个 kernel_\* 仓**（含 `kernel_uniproton` 这一常被忽略的实时内核）。

### 3.6 HCK：Linux 侧的「内核解耦」机制（易被漏掉的一环）
[`kernel-standard-hck.md`](https://gitee.com/openharmony/docs/raw/master/zh-cn/device-dev/kernel/kernel-standard-hck.md)：
> “社区开发设计HCK（OpenHarmony Common Kernel）内核解耦框架，该方案为开发者提供了整套插桩、注册、调用接口，减少对内核的侵入修改”

四个宏：`DECLARE_HCK_LITE_HOOK` / `REGISTER_HCK_LITE_HOOK` / `REGISTER_HCK_LITE_DATA_HOOK` / `CALL_HCK_LITE_HOOK`；开关 `CONFIG_HCK=y`、`CONFIG_HCK_VENDOR_HOOKS=y`；头文件放 `kernel-x.x/include/linux/hck/lite_hck_*.h`，命名后缀 `_lhck`；示例在 `linux-5.10(or linux-6.6)/samples/hck`。**它和 KAL 是两回事**：KAL 面向「上层接口统一」，HCK 面向「厂商特性以插桩方式少侵入内核」，二者共同降低多平台维护成本。

## 5. 内核适配层：KAL 与 HDF 如何落在不同内核上

### 5.1 KAL 的定位
[`kernel-overview.md`](https://gitee.com/openharmony/docs/raw/master/zh-cn/device-dev/kernel/kernel-overview.md)：
> “多个内核通过KAL（Kernel Abstraction Layer）模块，向上提供统一的标准接口”

> “内核抽象层（KAL，Kernel Abstract Layer）通过屏蔽内核间差异，对上层提供基础的内核能力”

[docs.openharmony.cn](https://docs.openharmony.cn/) 技术架构页给出 KAL 覆盖范围：
> “包括进程/线程管理、内存管理、文件系统、网络管理和外设管理等”

落地形态因内核而异：
- LiteOS-M：`kernel/liteos_m/kal/{cmsis,posix,libc}`（CMSIS-RTOS2 + POSIX 子集 + musl/newlib）；
- LiteOS-A：无 `kal/` 目录，改由 `compat/posix/`（POSIX 兼容）+ `bsd/`（FreeBSD 驱动/适配）+ `syscall/` 承担同类职责；
- Linux：直接复用 Linux syscall + musl，KAL 的「统一」由用户态 libc/系统服务层消化。

### 5.2 HDF 的三层解耦
[`driver-overview-foundation.md`](https://gitee.com/openharmony/docs/raw/master/zh-cn/device-dev/driver/driver-overview-foundation.md)：
> “HDF驱动架构采用C语言面向对象编程模型构建，通过平台解耦、内核解耦，来达到兼容不同内核”

> “操作系统抽象层（OSAL，Operating System Abstraction Layer）：提供统一封装的内核操作相关接口，屏蔽不同系统操作差异，包含内存、锁、线程、信号量等接口”

仓库分工（同文表 1）：
| 路径 | 内容 |
|---|---|
| `drivers/hdf_core/framework` | 平台无关框架、平台驱动框架、驱动模型 |
| `drivers/hdf_core/adapter` | “包含所有LiteOS-M和LiteOS-A内核以及用户态接口库等相关适配代码” |
| `drivers/hdf_core/adapter/khdf/linux` | “包含所有Linux内核相关适配代码以及编译脚本” |

源码验证（访问 2026-11-02）：
- `adapter/khdf/linux/Makefile`、`adapter/khdf/liteos/Makefile`、`adapter/khdf/liteos_m/BUILD.gn` 三个目录真实存在 → L-A / L-M / Linux 各一份内核态适配。
- `adapter/khdf/linux/patch_hdf.sh` 把 `drivers/hdf_core/adapter/khdf/linux` **软链为内核树内的 `drivers/hdf/khdf`**，再套 `common_patch/hdf.patch`，即 HDF 以 in-tree 模块形式编进 Linux。
- 仓内 `AGENT.md`（较新、描述性）称 khdf 支持 “Linux、LiteOS-A、LiteOS-M、UniProton、HongMeng”，且 “OSAL 层按内核分目录：Linux 在 `adapter/khdf/linux/osal/`，LiteOS-A 在 `adapter/khdf/liteos/osal/`，LiteOS-M 在 `adapter/khdf/liteos_m/osal/`”。

### 5.3 SoC 厂商在「内核层」到底要做什么

**A. 轻量系统（LiteOS-M）** — [`porting-minichip-kernel.md`](https://gitee.com/openharmony/docs/raw/master/zh-cn/device-dev/porting/porting-minichip-kernel.md)：
1. 架构移植（可选）：“如果当前OpenHarmony已经支持对应芯片架构则不需要移植”；否则实现 `arch/include` 下 `los_arch.h / los_atomic.h / los_context.h / los_interrupt.h / los_timer.h`。
2. 接厂商 SDK：放 `device/<Vendor>/<Board>/`，`BUILD.gn` 链接闭源静态库、指定 `-T xxx.ld` 链接脚本、objcopy 出 bin。
3. 写 `target_config.h`（`OS_SYS_CLOCK`、`LOSCFG_BASE_CORE_TICK_PER_SECOND`、`LOSCFG_PLATFORM_HWI`、`LOSCFG_BASE_CORE_TSK_LIMIT`、各 IPC limit…），覆盖 `los_config.h` 默认值。
4. 中断接管两选一：`LOSCFG_USE_SYSTEM_DEFINED_INTERRUPT=NO` 时改启动文件（`PendSV_Handler→HalPendSV`、`SysTick_Handler→OsTickHandler`）；或置 YES 走重定向（`g_hwiForm` 需按 arch 手册对齐，通常 0x200）。
5. `config.json` 挂 `"subsystem": "kernel"` → `liteos_m`；`BUILD.gn` 里开关 `enable_ohos_kernel_liteos_m_kal` 等特性。
6. 驱动：资源极度受限时官方建议用 **IoT 子系统**（`base/iot_hardware/peripheral` 的 GPIO/I2C/PWM/UART/WATCHDOG HAL），而非 HDF（[porting-minichip-subsys-driver.md](https://gitee.com/openharmony/docs/raw/master/zh-cn/device-dev/porting/porting-minichip-subsys-driver.md)）。

**B. 小型系统（LiteOS-A）** — [`porting-smallchip-kernel-a.md`](https://gitee.com/openharmony/docs/raw/master/zh-cn/device-dev/porting/porting-smallchip-kernel-a.md) 七步：
1. 新增 `target_config.h`：`DDR_MEM_ADDR` / `DDR_MEM_SIZE`，供 `board.ld.S` 展开成 `board.ld`；
2. 定义 MMU 全局映射数组 `g_archMmuInitMapping`（段属性 + 虚实映射）；
3. 多核则实现 `struct SmpOps`（`SmpCpuOn` 唤醒从核）并 `LOS_SmpOpsSet` 注册，`LOS_MODULE_INIT(..., LOS_INIT_LEVEL_EARLIEST)`；
4. 链接脚本生成镜像；
5. 单核入口 `reset_vector_up.S` / 多核 `reset_vector_mp.S`（中断向量表、MMU 页表）；
6. 跳 C 语言 `main`，初始化时钟/软定时器/内存/任务，创建 `SystemInit` 任务并 `OsSchedStart()`；
7. `SystemInit` 中调 `DeviceManagerStart` 启动 HDF，读取单板 `hdf.hcs`。
另有启动层级表 `LOS_INIT_LEVEL_EARLIEST → … → LOS_INIT_LEVEL_KMOD_TASK`，官方建议“推荐关注 ARCH 至 KMOD_TASK 之间”。

**C. 标准系统（Linux）** — 两条路线，[`standard-system-porting-guide.md`](https://gitee.com/openharmony/docs/raw/master/zh-cn/device-dev/porting/standard-system-porting-guide.md) 与 [`porting-linux-kernel.md`](https://gitee.com/openharmony/docs/raw/master/zh-cn/device-dev/porting/porting-linux-kernel.md)：
- 路线一（推荐给三方）：`OH 内核态层 = 三方 LTS Linux + OH 内核态基础代码(hilog/hievent) + OH 内核态特性(HDF)`。
  1. 三方内核拷进构建树 `out/KERNEL_OBJ/kernel/src_tmp/linux-xxx`；
  2. 移植 `drivers/staging/hilog`、`hievent`，改 `Kconfig/Makefile`，开 `CONFIG_HILOG/CONFIG_HIEVENT`；
  3. 跑 `patch_hdf.sh <工程根> <内核目录> <补丁路径> <设备名>` 打 HDF 补丁；
  4. 开 `CONFIG_DRIVERS_HDF=y`、`CONFIG_HDF_SUPPORT_LEVEL=2`、`CONFIG_DRIVERS_HDF_PLATFORM_{GPIO,I2C,UART,MIPI_DSI}=y` 等；
  5. 验证 init → shell → NFS。
- 路线二（用 OH 基线）：写 `<chip>_small_defconfig`（由 `small_common_defconfig` + 芯片 config 合成）→ 建 `patches/linux-X.Y/<chip>_patch/`（含 `hdf.patch`）→ 改 `kernel.mk`/`kernel_module_build.sh` 的 patch 路径、编译器、架构、Image 格式 → 烧录 + bootargs（Hi3516DV300 示例：`mem=128M console=ttyAMA0,115200 root=/dev/mmcblk0p3 …`）。
- SoC 厂商最小工作量归纳：**defconfig + 板级 patch（DTS/DRM/MMC 等）+ HDF 补丁适配 + init/rootfs 起来**。
