### 1.3 启动链（uboot 来自 SDK，ATF 承载 BL33）

```

        → 读 kernel 分区到 0x5007FFC0（uImage 实际入口 0x50080000）

```
- 实测 `uboot_env_4GB.txt`：`bootcmd=...mmc read 0 ${fip_addr}...;mmc read 0 ${kernel_addr}...;auto_burn;bootm ${fip_addr}`，`fip_addr=0x50000000`，`kernel_addr=0x5007FFC0`。

### 3.1 `linux-6.6/hispark_aifly_patch/` —— **编号序列**（与 p7885/rk3568 不同）

| 文件 | 大小 | 作用（据文件名/内容） |

| `0005-kernel-dhcp-support.patch` | 1 KB | gmac `rgmii-id→rgmii`、DMA mask 64→32 |
| `0006-kernel-mipi-support.patch` | 487 B | MIPI |
| `0007-kernel-nca9555.patch` | 13 KB | NCA9555 IO 扩展 |

对比：
- `linux-6.6/p7885_patch/` = **单个 `kernel.patch`**

→ **编号序列是 Hi3403 的刻意选择**：10 个关注点分离、可单独回退、可增量追加。这就是"新 SoC 模板"推荐的补丁组织法。

### 3.2 合并脚本关键逻辑（可为新 SoC 复用）

```sh
apply_patch() {
  if patch -p1 --dry-run < "$f" >/dev/null 2>&1; then patch -p1 < "$f" || exit 1
  elif patch -p1 --dry-run -R < "$f" >/dev/null 2>&1; then echo "Already applied, skipping"
  else echo "Failed to apply patch: $f" >&2; exit 1; fi
}
sync_dt_bindings   # 把 include/dt-bindings/** 软链进 scripts/dtc/include-prefixes/
```
→ 解决两个真实痛点：**重复编译幂等** + **DTC 找不到新增 dt-bindings 头**。

### 3.3 `kernel_linux_build/kernel.mk`（HEAD `f99b7582473a9a92a2a09d9d94719728ec913994`，2026-07-24）

通用构建器只认"单文件/双文件"约定：
```make
DEVICE_PATCH_DIR  := $(OHOS_BUILD_HOME)/kernel/linux/patches/${KERNEL_VERSION}/$(DEVICE_NAME)_patch
DEVICE_PATCH_FILE := $(DEVICE_PATCH_DIR)/$(DEVICE_NAME).patch
SMALL_PATCH_FILE  := $(DEVICE_PATCH_DIR)/$(DEVICE_NAME)_$(BUILD_TYPE).patch
```
linux-6.6 额外变量（仅 6.6 生效）：`OH_HEADERS_PATCH_FILE`、`WATCHDOG_PATCH_FILE`、`MD_STOP_WRITES_PATCH_FILE`、`KVM_FIX_PATCH_FILE`，以及通用 `code_sign/hideaddr/newip/tzdriver/xpm/ced/qos_auth/dec/ucollection` 系列 `apply_*.sh`。

**但 hispark_aifly 并不走这套**：它用 `device/board/hisilicon/hispark_aifly/kernel/kernel.mk` 自己实现，差异点正是新 SoC 必须补的：
1. `chmod +x patch_hispark_aifly.sh` 并调用编号脚本（而非 `patch -p1 < *.patch`）
2. **HDF 驱动软链进内核树**：
   ```make
   ln -sfn $(OHOS_BUILD_HOME)/device/soc/hisilicon/hi3403v100/hdf_driver \
           $(KERNEL_SRC_TMP_PATH)/drivers/hdf/soc_driver
   ```
3. defconfig 四段合并：`small_defconfig → <board>/arch/arm64_defconfig → <board>/arch/support_defconfig → base_defconfig`
4. 额外对 4 个 DRM ko 调 `batch_sign_ko.sh`（`CONFIG_MODULE_SIG` 强制）
5. `bounds_checking_function/securec.h` 的 `<stdarg.h>` → `<linux/stdarg.h>`（仅 6.6）

## 7. 矛盾点与风险（写作时别踩）

1. **文档 vs 仓库布局**：指南「版本烧写」用 `20M(kernel)`、`root=/dev/mmcblk0p4`、无 fip 分区；仓库 `bootloader/bootargs` 用 `512K(fip)+19968K(kernel)`、`p5`。→ 以仓库为准。
2. **同名 manifest 两份**：`openharmony-sig/manifest@devboard_hispark_aifly_5.1.0.xml`（444 project，gitee/gitcode 远端，kernel 仓未注释）vs `HiSpark/Hi3403V100@os/OpenHarmony/manifest/...`（gitee SSH，kernel_config/patches/5.10 被注释）。→ 复现必须说明用哪份。
3. **aiflylite 产品缺失**：文档给出 `ipcamera_hispark_aiflylite_linux` 编译命令，但三个公开仓中 **没有** `vendor/hisilicon/hispark_aiflylite_linux/`，也无该 `product_name`；仅代码里有 `board_name == "hispark_aiflylite"` 分支（`device_soc/.../hi3403v100/BUILD.gn:27`、`common/hal/media/BUILD.gn:16`）。→ Hi3519AV200 变体在公开仓**不可直接编译**。
4. **"支持所有 XTS 用例"是厂商表述**：文档写"满足媒体和图形Sample功能及所有XTS用例"，但同文又给出 2 个 acts 用例修补（`testDisConnectAbility`、`testIPCClient0130`）与 HUKS KEY0 前提。→ 引用时应加限定。
5. **毕业状态**：代码已进主线但 SIG 评审 2026-10-20 又打回；不要写"已毕业/已合入主干完成"。
6. **主线 6.1 的 `--patch` 不需要**：若照抄 5.1 指南在 6.1-LTS 上加 `--patch`，会因 `patch.yml` 不存在而失败。
7. **DRM 默认值不一致**：指南称默认 DRM；SIG `config.json` 中 `graphic_utils_lite_enable_drm_display_hal=false`。需以实机/分支确认。
