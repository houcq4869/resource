## 三、标准系统 vs 轻量/小型系统

官方三种系统类型（Overview「系统类型」）：轻量 mini（最小 128 KiB，MCU）、小型 small（最小 1 MiB，Cortex-A）、标准 standard（最小 128 MiB，完整应用框架）。

**子系统清单按系统类型确实不同，而且是三套机制：**

| 系统类型 | 配置入口 | 子系统数（6.0 主干） | 证据 |
|---|---|---|---|
| 标准 standard | `build/subsystem_config.json` + `vendor/<产品>/config.json` + `productdefine_common/inherit/*.json` | 配置表 57；实际产品 phone 47 / tablet 47 / 2in1 45 / tv 40 / rich 54 | `productdefine_common/inherit/phone.json` 等 |
| 小型 small | `build/lite` + `productdefine_common/base/small_system.json` | 16（ability/arkui/kernel/multimedia/xts…） | `base/small_system.json` |
| 轻量 mini | `build/lite` + `productdefine_common/base/mini_system.json` | 7 唯一（commonlibrary/communication/hiviewdfx/security/startup/thirdparty/updater） | `base/mini_system.json`（8 条含重复 communication） |

证据（访问 2026-11-02）：
- https://gitee.com/openharmony/productdefine_common/blob/5b448beb96a0af97cafd757a3115132df95386d6/inherit/phone.json

## 四、子系统 → 仓库的映射机制（4 层链条，无 monorepo）

`gitee.com/openharmony/openharmony` **不存在**；真正的「工作区」由 repo 按 manifest 拼出：

**第 1 层：manifest 决定「有哪些仓、落在哪个路径、属于哪类系统」**
`manifest/ohos/ohos.xml` 共 **496 个 `<project>`**，形如：

```xml
<project groups="default,ohos:standard,ohos:system"
         name="arkui_ace_engine"
         path="foundation/arkui/ace_engine"
         remote="gitcode" revision="master"/>
```

`default.xml` 汇总 `ohos/ohos.xml` + `chipsets/all.xml`；`default remote="gitcode"`（Gitee 为镜像）。
https://gitee.com/openharmony/manifest/blob/88874afe039b6467430f26bbf519b75910523ddc/ohos/ohos.xml

group 的官方语义（manifest README）：`ohos:mini` / `ohos:small` / `ohos:standard` / `ohos:system`（与硬件无关、产物在 `/system`）/ `ohos:chipset`（产物在 `/vendor`、`/chipset`）。
https://gitee.com/openharmony/manifest/blob/88874afe039b6467430f26bbf519b75910523ddc/README.md

**第 2 层：`build/subsystem_config.json` 决定「子系统 → 源码根目录」**
6.0 共 **57 项**，如 `"arkui": {"path": "foundation/arkui", "name": "arkui"}`。
https://gitee.com/openharmony/build/blob/c5f750490301be95ece79ff6a274b15bef8378a4/subsystem_config.json

**第 3 层：产品 `config.json` 决定「这个产品要哪些子系统/部件/特性」**
`vendor/hihope/rk3568/config.json`：`"type": "standard"`，`inherit: ["productdefine/common/inherit/rich.json", ".../chipset_common.json"]`，并显式列 `arkui → ace_engine, ui_appearance`。
https://gitee.com/openharmony/vendor_hihope/blob/master/rk3568/config.json

**第 4 层：每个部件仓根目录 `bundle.json` 自描述「我属于哪个子系统、装到哪个路径、编译哪些模块」**

```json
"segment": { "destPath": "foundation/arkui/ace_engine" },
"component": { "name": "ace_engine", "subsystem": "arkui", "syscap": [...] }
```
https://gitee.com/openharmony/arkui_ace_engine/blob/master/bundle.json

**构建期落地**：Preloader 解析产品 `config.json` → 生成 `out/preloader/<product>/parts.json`、`subsystem_config.json`；Loader 读各仓 `bundle.json` 生成部件列表；GN/Ninja 编译。官方原文：“产品的配置文件为config.json，放在vendor目录的产品目录下”“子系统的配置文件为build仓下的subsystem_config.json”“部件的配置文件为bundle.json”。
https://gitcode.com/openharmony/build/blob/master/docs/%E7%BC%96%E8%AF%91%E9%85%8D%E7%BD%AE%E6%8C%87%E5%AF%BC%E6%96%87%E6%A1%A3.md

**一句话总结映射链**：
`subsystem_config.json`（子系统→目录）+ `bundle.json`（部件→子系统/路径）+ `vendor config.json`（产品→部件）+ `ohos.xml`（路径→仓名/URL/系统类型）→ Preloader 生成 parts.json → GN。

## 六、口径冲突与使用注意（研究结论）

1. **三套清单不能混用**：29（概览表，含适用范围）/ 44（子系统 readme，有详细职责）/ 57（构建配置，可编译）。写文档应声明口径。
2. **「系统基本能力」vs「系统基础能力」**：Overview 用“基本”，sourcecode-acquire 表用“基础”。同一概念两种官方写法。
3. **「安全」「权限」归属自相矛盾**：散文归“系统基本能力”，代码在 `base/`（官方定义为“基础软件服务&硬件服务”）。
4. **`base/` 是混合目录**，不能仅凭目录判定“基础软件服务”还是“硬件服务”；本表对 location/useriam/iothardware 用官方举例，对 sensors/usb/tee 标注“推断”。
5. **“增强软件服务子系统集”在开源主干几乎为空**：只有 `domains/advertising`，官方举例的智慧屏/穿戴/IoT 专有业务不在开源仓，落在 `vendor/`。
6. **“monorepo”是误称**：真正的单仓 `openharmony/openharmony` 不存在；`repo init -u .../manifest` 才是入口。
7. **Gitee 仍是镜像，官方主库已切 GitCode**：6.0 Overview“代码仓地址”写 `https://gitcode.com/openharmony`；本表仓名在 Gitee/GitCode 同名可用（已确认 `arkui_ace_engine`、`communication_dsoftbus`、`graphic_graphic_2d`、`multimedia_audio_framework`、`ability_ability_runtime` 在 Gitee 存在）。
