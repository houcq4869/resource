# 01 · 分层架构总览（源码解读系列）

## 1. 官方四层架构 ↔ 源码目录映射

官方定义（`docs/zh-cn/OpenHarmony-Overview_zh.md`）：自下而上 = **内核层 → 系统服务层 → 框架层 → 应用层**，系统功能按「**系统 > 子系统 > 组件**」逐级展开，支持按需裁剪。

| 逻辑层 | 官方内容 | 源码落点 | 说明 |
|---|---|---|---|
| 内核层 | 内核子系统（多内核 Linux/LiteOS + KAL 内核抽象层）、驱动子系统(HDF) | `kernel/`、`drivers/` | 物理映射最干净的一层 |
| 系统服务层 | 四个子系统集：系统基本能力 / 基础软件服务 / 增强软件服务 / 硬件服务 | `foundation/`、`base/`、`domains/` | **逻辑分层 ≠ 物理目录**：目录只有三种子系统集名（foundation/base/domains），与官方四子系统集口径并不一一对应（调研报告 02 详档已分析此口径分歧） |
| 框架层 | 多语言用户程序框架、Ability 框架、ArkUI、多语言 API | 分散在 `foundation/ability`、`foundation/arkui`、`interface/`、`arkcompiler/` | 「框架」是能力概念，没有单一框架目录 |
| 应用层 | 系统应用 + 三方应用 | `applications/`；三方应用装机而来（HAP 包，不在源码树） | 系统应用与普通应用**同构**（都是 HAP） |

**关键认知：分层是逻辑视图，目录是构建视图。** 读代码时用目录定位，讲架构时用分层。

> 【文档滞后示例】官方 Overview 至今写「应用由 FA/PA 组成」——FA/PA 是已废弃的 FA 模型概念，6.x 主推 **Stage 模型**（UIAbility/ExtensionAbility，阶段 4 详讲）。官方总览文档更新慢于代码，源码才是最终事实。

## 2. 三种系统形态的源码证据

官方口径（Overview 文档「系统类型」节）：

| 形态 | 定位 | 最小内存 | 内核 |
|---|---|---|---|
| 轻量 mini | MCU（Cortex-M / RISC-V 32） | 128 KiB | LiteOS-M |
| 小型 small | 应用处理器 Cortex-A | 1 MiB | LiteOS-A 或 Linux |
| 标准 standard | Cortex-A + GPU/合成 | 128 MiB | Linux（6.1 默认 6.6） |

**源码证据链**（本仓库实测）：

1. **`productdefine/common/base/`** 存在 `mini_system.json` / `small_system.json` / `standard_system.json` 三份基础拼装清单——形态差异从产品定义第一层就开始：
   - mini：8 个子系统（hiviewdfx/startup/communication/security/commonlibrary/updater/thirdparty + …），**无图形、无窗口、无应用框架**；
   - small：16 个子系统，**开始出现 graphic/window/arkui/multimedia/ability**（轻量版本）；
   - standard：14+ 子系统，出现 resourceschedule/customization 等，再叠加 inherit 轮廓后规模爆炸（见 §3）。

2. **`vendor/<厂商>/<产品>/config.json`** 的 `type` + `kernel_type` 字段是形态的直接声明：
   - `vendor/hisilicon/hispark_pegasus/config.json`：`type: "mini"`，`kernel_type: "liteos_m"`，12 个子系统，第三 方件指向 `device/soc/hisilicon/hi3861v100/sdk_liteos`（芯片 SDK 裸奔形态）；
   - `vendor/hisilicon/hispark_taurus/config.json`：`type: "small"`，`kernel_type: "liteos_a"`，21 个子系统（含 graphic/window/sensors/ai）；
   - 标准系统（RK3568 等）：`kernel_type` 为 linux，部件量级见下节。

3. `kernel/` 目录本身就是形态分野的物理证据：`liteos_m`（mini）/ `liteos_a`（small）/ `linux-5.10`+`linux-6.6`（standard，6.6 为默认）/ `uniproton`（实时内核，可组合）。

**一句话总结形态差异**：mini 是「带通信栈的固件」，small 是「轻量带屏系统」，standard 是「完整应用平台」。三者**共享同一套构建与部件体系**（subsystem/component 机制一致），差异只在于选了哪些部件——这就是「统一 OS、弹性部署」在工程上的实现方式。

## 3. 「系统 > 子系统 > 部件」与产品拼装机制

### 3.1 三级单元

| 单元 | 注册处 | 本仓库实例 |
|---|---|---|
| 子系统（逻辑分组） | `build/subsystem_config.json`（59 个，含 `path` 指向目录） | `"arkui": {"path": "foundation/arkui"}` |
| 部件（构建单元，bundle） | 各仓 `bundle.json` | `foundation/ability/ability_runtime/bundle.json` → 部件 `ability_runtime`，`subsystem: "ability"`，`adapted_system_type: ["standard"]` |
| 仓（git 单元） | `.repo/manifests/ohos/ohos.xml`（494 平台仓） | 一个仓可含多个部件（目录即部件） |

### 3.2 产品拼装 = 四层 JSON 叠加

```
① base 清单（按形态）   productdefine/common/base/{mini,small,standard}_system.json
② inherit 轮廓（按设备形态） productdefine/common/inherit/{rich,phone,tv,tablet,wearable,2in1,
                          headless,ipcamera,liteWearable,chipset_common}.json
③ 通用产品             productdefine/common/products/system_arm_default.json
④ 厂商产品             vendor/<公司>/<产品>/config.json  (+ device/board/*, device/soc/*)
```

实测数据：`system_arm_default.json` 本体只声明 2 个子系统 4 个部件（selinux_adapter + 三个 drivers_peripheral_*），`inherit: ["productdefine/common/inherit/rich.json"]` 继承 **55 个子系统 / 315 个部件**——标准系统的完整规模。

`inherit/` 目录本身就是一部「设备形态字典」：phone / tablet / tv / wearable / 2in1 / headless（无屏）/ ipcamera / liteWearable……**每种产品形态在工程上就是一份部件清单**。

### 3.3 部件依赖网（`bundle.json` 的 `deps`）

以 `ability_runtime`（应用运行时）为例，其 deps 引用：ace_engine(ArkUI 引擎)、ets_runtime/ets_frontend(ArkTS)、bundle_framework(包管理)、dsoftbus(软总线)、common_event_service、data_share、ffrt(并发框架)……——一张部件级依赖图，预告了后续阶段的解读对象。`adapted_system_type` 字段则声明部件适用于哪些形态（如 ability_runtime 仅 standard）。

## 4. 本篇结论

1. 官方四层架构是**逻辑视图**；源码目录是**构建视图**；两者通过 `subsystem_config.json`（逻辑→目录）与 `bundle.json`（目录→部件）衔接。
2. 三种系统形态 = 三份 base 部件清单 + 不同内核选择；mini/small/standard 共享同一套部件体系。
3. 一个产品 = base(形态) → inherit(设备轮廓) → 产品(通用) → vendor(厂商) 四层 JSON 合并出的**部件集合**，构建系统按集合 + 依赖闭包编译出镜像。
4. 官方文档有滞后（FA/PA 表述），源码为最终事实。
