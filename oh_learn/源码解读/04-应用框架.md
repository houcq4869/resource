# 04 · 应用框架（源码解读系列）

> 对象：`~/workspace/oh_lts`（OpenHarmony 6.1 LTS）· 只读解读 · 2026-11-12
> 本篇回答：Stage 模型的代码本体在哪？一个应用从点击图标到上屏，代码路径怎么走？ArkUI 与图形栈如何分层？

---

## 1. 全景：应用框架 = 三个子系统 + 一个进程机制

```
foundation/ability     AbilityRuntime（应用/能力运行时）—— 调度与生命周期
foundation/arkui       ArkUI（声明式 UI 框架）—— 界面描述与驱动
foundation/graphic     图形栈（RenderService）—— 渲染与合成
base/startup/appspawn  应用进程孵化（zygote 等价物）
foundation/window      窗口管理（windowmanager，本篇略、阶段5涉及）
```

## 2. AbilityRuntime 解剖（`foundation/ability/`）

### 2.1 目录构成

```
ability/
├── ability_base        基础对象：Want、AbilityResult 等公共定义
├── ability_runtime     ★ 主仓（本节主角）
├── ability_lite        轻量系统版（mini/small 的 Ability 框架）
├── ability_cangjie_wrapper   仓颉语言接入层
├── dmsfwk(_lite)       分布式任务调度框架（跨设备迁移/远程启动，阶段 5）
├── form_fwk            卡片（Form）框架
└── idl_tool            IDL 工具
```

### 2.2 `ability_runtime` 的「双侧结构」—— 系统侧管理 + 应用侧执行

**系统侧（`services/`，跑在系统服务进程）**：

| 服务 | 职责 |
|---|---|
| `abilitymgr` | AbilityManagerService：Ability 生命周期调度、启动/切换/迁移决策 |
| `appmgr` | AppMgrService：应用进程级管理（与 appspawn 交互） |
| `dataobsmgr` | 数据观察者管理 |
| `quickfixmgr` | 热修复管理（对接 ets_runtime/quick_fix） |
| `dialog_ui` | 系统对话框 |
| `uripermmgr` | URI 权限管理 |
| `service_router_framework` | 服务路由（应用内跳转治理） |
| `agent_runtime_framework` | **Agent 运行时框架（6.x 新增，AI 应用形态）** |

**应用侧（`frameworks/`，编进每个应用）**：`c / native / ets / js / cj` 五套语言绑定——**同一套 Ability 框架对 C/C++/ArkTS/JS/仓颉五种语言开放**；`js_environment / ets_environment / cj_environment` 是各语言的运行时环境桥（ArkTS 环境桥接方舟 VM）。另有 `simulator`（模拟器支持）。

### 2.3 Stage 模型要点（对照代码）

- **UIAbility**：有界面的应用组件，生命周期（Create→Foreground→Background→Destroy）由 `abilitymgr` 调度、`frameworks/native` 执行；
- **ExtensionAbility**：无独立入口的场景化扩展（Form/InputMethod/Accessibility 等，由对应系统服务拉起）；
- **Want**：启动意图（`ability_base` 中的公共对象，等价 Intent）；
- **AbilityStage / Context**：应用级回调与环境句柄（`frameworks/ets` 内实现，暴露给 ArkTS 的 `AbilityStage` 基类即在此）。

> FA 模型（FA/PA）仅存于文档表述与 `ability_lite`（轻量系统仍用），标准系统 6.x 全面 Stage 化。

### 2.4 进程机制：appspawn（`base/startup/appspawn`）

应用进程孵化器，功能等价 Android zygote 但实现独立：模板进程预热 + fork + 按需特化。本仓实证其**沙箱配置族**：`appdata-sandbox-app.json / -debug.json / -gpu.json / -asan.json`——不同应用类型（普通/调试/GPU 加强/ASan 检测）走不同沙箱配置。应用进程内嵌 ArkTS VM（阶段 3 的 `daemon/`+`js_vm` 即配合此机制）。

## 3. ArkUI 解剖（`foundation/arkui/`）

```
arkui/
├── ace_engine          ★ 主引擎（标准系统）
├── ace_engine_lite / ui_lite   轻量系统的 UI 引擎（mini/small）
├── advanced_ui_component       高级组件库（XComponent 等）
├── arkui_cangjie_wrapper       仓颉版 ArkUI 接入
├── napi                        ArkUI NAPI 接口
└── ui_appearance               外观（深色模式等系统级 UI 设置）
```

### `ace_engine/frameworks/` 的关键结构

- `base` + `core`：引擎基座（组件树、布局、动画、事件、状态管理 V1/V2 等核心机制）；
- `bridge/` —— **前端家族**，一个引擎多套前端：
  - `declarative_frontend`：声明式主前端（ArkUI 的正统，ArkTS DSL）；
  - `js_frontend`：类 Web 范式（HML/CSS/JS，旧 FA 时代前端，维护态）；
  - `card_frontend`：卡片前端（Form 场景）；
  - `cj_frontend`：**仓颉前端**（仓颉版声明式 UI 的落点）；
  - `plugin_frontend`：插件形态。
- `component_ext`：组件扩展机制；根目录还有《如何新增一个组件.md》《组件化重构通用方案.md》等社区工程文档。

**解读**：ArkUI 的「声明式」= 状态驱动 UI（`@State` 等装饰器 → 状态变更 → 最小化更新组件树），执行层跑在方舟 VM 上，与 ets_runtime 紧耦合（ace_engine 是 6.x 前端编译的默认目标）。

## 5. 一条主线：点击图标到上屏的代码路径（综合 2~4）

```
点击图标（Launcher，本身是 HAP）
  → BMS(bundlemanager) 查包 → AMS(abilitymgr) 决策
  → appspawn fork 应用进程（沙箱按 appdata-sandbox-app.json 特化）
  → 进程内初始化 ArkTS VM + AbilityRuntime(frameworks/native)
  → 加载 HAP 的 .abc，执行 AbilityStage → UIAbility 生命周期
  → ArkUI declarative_frontend 建 UI 组件树，状态绑定
  → 每帧：布局/绘制 → render_service_client 生成绘制指令(DisplayList)
      经 BufferQueue(graphic_surface) 提交
  → RenderService(render_service 进程) 统一渲染
  → composer + 显示 HDI → 上屏
```

关键架构判断：**UI 与渲染分离**——应用进程只产生绘制指令，真正的绘制与合成集中在系统 RenderService 进程（多窗口统一合成、跨窗口协同的根基；与 Android 每应用自绘 + SurfaceFlinger 合成的模式相比，把更多渲染智能上收）。

## 6. 多语言接入的完整证据链（本仓实测）

同一应用框架，四路语言接入层全部在仓：`ability_cangjie_wrapper` / `arkui_cangjie_wrapper` / `graphic_cangjie_wrapper`（仓颉三件套）+ `ace_engine/frameworks/bridge/cj_frontend` + `ability_runtime/frameworks/cj` + `frameworks/ani`（ArkTS Native Interface）。**仓颉不是外挂，是框架一级公民**。另有 `agent_runtime_framework` 预示 AI Agent 应用形态进入框架层。

## 7. 本篇结论

1. 应用框架 = **双侧结构**：系统侧服务（abilitymgr/appmgr 调度决策）+ 应用侧框架（五语言绑定、编进每个应用）；
2. 进程模型 appspawn ≈ zygote，但沙箱配置化程度更深（分类型沙箱 JSON）；
3. ArkUI 一引擎多前端（declarative 主 + card/cj/legacy），声明式与方舟 VM 深度耦合；
4. 图形栈把渲染上收到系统 RenderService 进程，应用只产指令——多窗口与跨设备协同的架构基础。
