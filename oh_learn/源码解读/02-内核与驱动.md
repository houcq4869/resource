# 02 · 内核与驱动（源码解读系列）

> 对象：`~/workspace/oh_lts`（OpenHarmony 6.1 LTS）· 只读解读 · 2026-11-10
> 本篇回答：多内核体系如何组织？OpenHarmony 对 Linux 改了什么？LiteOS-M/A、Uniproton 各是什么？HDF 如何实现「一次开发、多系统部署」？

## 1. `kernel/` 全景：多内核按需选择

```
kernel/
├── linux/          标准系统/small(Linux版)内核 —— linux-5.10（维护）+ linux-6.6（6.1 默认）
├── liteos_a/       small 形态内核（Unix-like，POSIX/BSD 兼容）
├── liteos_m/       mini 形态内核（组件化 RTOS）
├── uniproton/      实时内核（openEuler 孵化，工业控制定位）
（kernel_unisoc_p7885/ —— 芯片厂商内核仓，见阶段 0）
```

形态→内核映射（阶段 1 已证）：mini→liteos_m；small→liteos_a 或 linux；standard→linux（6.6 默认）。

## 2. Linux 内核线：OpenHarmony 的改动哲学 = 「主线内核保持干净」

`kernel/linux/` 自身不含内核源码本体（内核源码是独立仓 `kernel_linux_6_6` 挂载为 `linux-6.6/` 目录），本仓提供的是**组织层**：

| 目录/文件 | 作用 |
|---|---|
| `patches/linux-6.6/common_patch/` | **全系统通用补丁，实测仅 1 个：`hdf.patch`**（HDF 驱动框架接入内核） |
| `patches/linux-{4.19,5.10,6.6}/<板名>_patch/` | 板级补丁。实测 `hispark_aifly_patch/`：10 个编号补丁（DRM/VO/DHCP/MIPI/4G 模组/电源键 DTS…）+ `patch_hispark_aifly.sh` 一键脚本；另有 `rk3568_patch` |
| `common_modules/` | **内核态增量以可插拔模块实现，不改主线**：`tzdriver`(TLS 增强)、`newip`(新网络协议栈)、`code_sign`/`xpm`(代码签名与内存保护)、`dec`、`memory_security`、`container_escape_detection`、`ucollection`(采集)、`qos_auth`、`pac` —— OpenHarmony 的内核安全/特性体系全在这里 |
| `build/`（kernel.mk、kernel_build.py、build_kernel.sh） | 构建胶水：取内核仓 + 按板打补丁 + defconfig 碎片 → 出内核镜像与模块 |
| `config/` | 按体系结构/arch 的内核配置组织 |

**解读结论**：对 Linux 的侵入被刻意压到最小——通用层仅一个 HDF 补丁，其余增量要么是独立模块（`common_modules`），要么是板级补丁（随板走）。这使内核升级（5.10→6.6）可以平滑进行，也解释了为什么 6.1 能同时维护两版内核。

## 3. LiteOS-M（mini 形态）：组件化 RTOS + KAL 的标准范本

```
kernel/liteos_m/
├── kernel/src/     核心原语：los_task / los_sched / los_event / los_mux / los_sem /
│                  los_queue / los_swtmr / los_tick / los_sortlink + mm(内存)
├── kal/            内核抽象层实现：cmsis / posix / libc / libsec
├── components/     可裁剪组件：fs, net, shell, trace, power, security, backtrace,
│                  cppsupport, dynlink, lmk/lms(内存调测), debugtools …
├── arch/           多 CPU 架构支持
└── Kconfig + config.gni   组件级裁剪配置
```

**KAL 在这里可以摸到**：同一个 `kernel/src`，`kal/cmsis` 提供面向嵌入式生态的 CMSIS 接口，`kal/posix` 提供面向可移植软件的 POSIX 接口——上层组件（fs/net/shell）一律通过 KAL 编程，不直接碰内核原语。这就是官方文档「内核抽象层屏蔽多内核差异」的落地形态。

## 4. LiteOS-A（small 形态）：Unix-like 内核

`kernel/liteos_a/` 是传统 Unix 树形结构：`syscall/`、`fs/`、`net/`、`compat/bsd`（BSD 兼容层）、`arch/`、`drivers/`、`shell/`、`security/`、`platform/`。与 LiteOS-M（RTOS）的本质区别：**多进程、虚拟内存、POSIX 系统调用**——支撑小型系统跑「真正的多进程程序」（如 IP Camera 的编解码管线）。

## 5. Uniproton：第三个轻量内核选项

`kernel/uniproton/`（源自 openEuler 社区）：定位**工业控制场景的实时内核**，主打极致低时延与混合关键性部署，支持 MCU 到多核 CPU。构建为 CMake（`CMakeLists.txt`/`build.py`），在 OpenHarmony 内通过 `uniproton.gni` 接入 GN 体系；源码组织 `src/{core, mem, net, fs, osal, security, arch, om(观测)}`。**与 LiteOS-M 并列的可选内核**，印证「多内核设计」是持续演进的开放机制，而非一句宣传语。

## 6. HDF 驱动框架：`drivers/` 的解剖

```
drivers/
├── hdf_core/            HDF 核心（跨内核的驱动框架本体）
│   ├── framework/core/      host(驱动宿主) / manager(驱动管理) / shared / common / sec
│   ├── framework/model/     器件模型：audio / camera / display / input / sensor / usb / network / storage / misc
│   ├── framework/support、tools、utils
│   ├── adapter/             内核适配层（Linux / LiteOS 各一套）
│   └── interfaces/inner_api
├── interface/           HDI 接口定义（IDL：audio / battery / bluetooth / camera / codec / …）
├── peripheral/          各外设 HDI 参考实现（audio / camera / display / wlan / sensor / …）
├── liteos/               轻量系统驱动适配
└── external_device_manager/  外设扩展管理（扩展设备管理服务）
```

三个机制要点（本仓库证据）：

1. **HCS 配置驱动一切**：硬件拓扑、驱动加载全在 `.hcs` 配置文件里。实测 `vendor/hisilicon/hispark_taurus/hdf_config/sensor/` 下按器件分目录（`proximity/proximity_apds9960_config.hcs`、`gyro/gyro_bmi160_config.hcs`…）——**换传感器 = 换一份配置**，不动框架代码；
2. **HDI = 驱动接口的 IDL**：`drivers/interface/` 用接口定义语言描述能力，生成用户态/内核态双端代码，`drivers/peripheral/` 提供参考实现——框架与器件通过接口解耦（标准系统大量驱动跑在**用户态**，形成 C/S 架构，驱动故障不致内核崩溃）；
3. **与内核的接合面极薄**：Linux 侧仅需 `hdf.patch` 一个通用补丁（§2），其余靠 `adapter/` 适配不同内核——这是「一次开发、多内核部署」的实现根基。

**进程模型**（代码入口指向 `framework/core/{manager,host}`）：DeviceManager 服务统一管理，各驱动按 Host 分组隔离加载，HCS 描述的节点树决定谁加载、绑定哪个驱动（细节可在阶段 2.5 按需下钻 hdf_core 源码）。

## 7. 本篇结论

1. OpenHarmony 内核策略 = **多内核并存 + 最小侵入 + 配置化接入**：Linux 保持主线干净（1 个通用补丁 + 板级补丁 + 可插拔模块），LiteOS 双内核服务轻量形态，Uniproton 补实时场景；
2. KAL 在 LiteOS-M 中有教科书式实现（cmsis/posix 双接口层）；
3. HDF 是「软总线之外」另一块生态基石：硬件差异被压进 HCS 配置与 HDI 接口，框架本身跨内核复用。
