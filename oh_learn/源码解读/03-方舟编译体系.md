# 03 · 方舟编译体系（源码解读系列）

> 对象：`~/workspace/oh_lts`（OpenHarmony 6.1 LTS）· 只读解读 · 2026-11-11
> 本篇回答：ArkCompiler 由哪些仓组成？ArkTS 从源码到执行经过什么链路？AOT/JIT 如何组织？仓颉在 6.x 处于什么状态？

---

## 1. `arkcompiler/` 组件全景

```
arkcompiler/
├── ets_frontend/    前端编译器：es2panda / ets2panda（ArkTS→ArkIR 字节码）、
│                    arkguard(混淆)、merge_abc、test262
├── runtime_core/    运行时中枢（Panda 基础设施）：isa(指令集 YAML 定义+模板代码生成)、
│                    assembler/disassembler(pandasm)、libpandafile(.abc 文件格式)、
│                    bytecode_optimizer、verifier、libabckit(字节码操作库)、
│                    static_core(静态编译语言 VM)、taihe、plugins
├── ets_runtime/     ArkTS 运行时（动态执行引擎，本篇主角）
├── toolchain/       调试器：inspector、adapter（对接 DevTools 调试协议）
├── jsvm/            应用内嵌 JS 引擎（JSVM Kit，应用自用 JS 运行时）
└── cangjie_ark_interop/  仓颉 ⇄ ArkTS 互操作
```

分工一句话：**前端编译（ets_frontend）产出字节码文件 `.abc`；运行时（ets_runtime）消费 `.abc` 并执行；runtime_core 提供两者共用的指令集/文件格式/汇编器等基础设施。**

## 2. 执行链路总览

```
开发期（构建机）                        运行期（设备）
────────────────                      ─────────────────────────────────────
.ets/.ts 源码                          应用进程内嵌 ArkTS VM
   │ es2panda 前端编译（DevEco/hvigor 调用）      │ 加载 .abc（libpandafile）
   ▼                                        ▼
ArkIR（方舟中间表示）                    ① interpreter 解释执行（快/慢 stub 两级）
   │ assembler                            ② 热点 → baseline JIT / 优化 JIT（ecmascript/jit、compiler/baseline）
   ▼                                        ③ PGO AOT 机器码（可选，an 文件）
.abc 字节码（打包进 HAP）                    ④ GC（ecmascript/mem）、IC、quick_fix(热修复)…
```

三级执行形态（解释 → JIT → AOT）与 ART 的演进路线同构，但字节码（ArkIR）从设计起就面向静态化类型（为 ArkTS 方言保留类型信息），这是 AOT 优化效果的基础。

## 3. `ets_runtime/ecmascript/` 深读（运行时内构，本仓实测目录）

| 目录 | 职责 |
|---|---|
| `interpreter/` | 字节码解释器：`fast_runtime_stub` / `slow_runtime_stub` 双速路径 |
| `compiler/` | **AOT 编译器**（`aot_compiler*`、`aot_file`、`aot_snapshot`）+ **baseline JIT**（`baseline/`）+ 各类 `*_stub_builder` |
| `jit/` | 优化 JIT（运行时机器码生成） |
| `deoptimizer/` | 逆优化（AOT/JIT 假设失效时回退解释器） |
| `ic/` | 内联缓存（属性访问加速） |
| `mem/` | GC 与堆管理 |
| `pgo_profiler/` | PGO 画像采集（产出 `.ap` ark-profile 文件） |
| `compiler_service/` | **系统侧 AOT 编译服务**：`ark_aot_compiler.cfg`、`system_framework_aot_enable_list.conf`（系统框架应用 AOT 白名单——系统应用默认走 AOT 的证据） |
| `daemon/` + `js_vm/` | 进程池/VM 实例管理（配合 appspawn 预热应用进程） |
| `quick_fix/` + `patch/` | 热修复（动态补丁，不改包重装） |
| `napi/` | NAPI（JS ⇄ C/C++ 互操作边界） |
| `jspandafile/` + `cross_vm/` | 合并 abc（whole-application 字节码）与跨 VM 支持 |
| `builtins/`、`containers`、`regexp/`、`intl/`、`module/` | 内建对象、容器库、正则、国际化、模块加载 |

### AOT 实操链（`docs/aot-guide_zh.md` 实录）

1. `hdc shell param set ark.profile true` 开画像 → 2. 预热应用，设备侧生成 `.ap` 文件 → 3. `hdc shell bm compile -m partial <bundleName>` 触发 AOT 编译 → 4. `bm dump` 查 `aotCompileStatus`。

约束：仅 Stage 模型、仅 64 位设备、仅 release 模式。**PGO（Profile-Guided Optimization）是方舟 AOT 的核心思想**：用运行期类型画像 + 静态类型信息预先生成优化机器码，首启即高性能。

## 4. `runtime_core/`：被低估的"基础设施层"

- `isa/isa.yaml` + 模板（`gen.rb`/`templates`）：**指令集以 YAML 声明，代码生成器产出一套实现**——改指令集不用手写多平台代码，这是方舟迭代速度的工程保障；
- `libpandafile`：`.abc` 文件格式实现（字节码容器）；
- `assembler`/`disassembler`（含 `abc2program`）：字节码 ⇄ 可读汇编；
- `bytecode_optimizer`：字节码级优化（构建期对 abc 再优化）；
- `verifier`：加载期字节码校验（安全边界）；
- `libabckit`：对外暴露的字节码操作库（三方工具链用）；
- `static_core`：面向静态类型语言（仓颉）的静态执行 VM。

## 5. 仓颉（Cangjie）在 6.x 的状态（`docs_cangjie/` 实录）

- 定位：**静态类型、静态编译**的 OH 应用开发语言，多范式 + 元编程（eDSL）+ 丰富标准库；开源生态已有 400+ 三方库；
- 关键事实：**仓颉 API 随 OpenHarmony 6.x 首次向应用开放**，当前覆盖 5 大类 22 个 Kit（ArkUI/ArkData/ArkWeb/Ability Kit 等），后续逐版本扩到全量；
- 已验证场景：美团骑手端（与 ArkTS/Python/JS 互操作 + 各 Kit 混合开发）、力扣（在线编程判题）、AI 对话类应用；
- 源码侧对应物：`arkcompiler/cangjie_ark_interop`（互操作）+ `runtime_core/static_core`（静态执行）。仓颉编译器本体（cjc）不在本仓，走 openharmony-sig 孵化。

## 6. 与 V8 / ART 的对比（解读视角）

| 维度 | V8（Chromium） | ART（Android） | 方舟 ets_runtime |
|---|---|---|---|
| 输入 | JS 源码/JIT 解析 | dex 字节码 | **.abc（ArkIR 字节码）** |
| 编译形态 | JIT 为主（Ignition→Sparkplug→Maglev/TurboFan） | 解释+JIT+AOT（dex2oat） | 解释+baseline JIT+优化 JIT+**PGO AOT** |
| 类型信息 | 动态（反馈式） | 静态（dex 带类型） | ArkTS 静态化方言（构建期语法检查） |
| 运行位置 | 浏览器/Node 进程 | zygote→app 进程 | **appspawn→应用进程内嵌 VM** |
| 生态接口 | N-API | JNI | **NAPI** |
| 调试 | DevTools/CDP | JDWP/Perfetto | **toolchain/inspector（对接 DevTools 体系）** |

路线判断：方舟在工程形态上最接近 ART（系统级 PGO AOT + JIT 混合），差异在字节码面向 TS 静态方言设计、且解释器路径保留给资源敏感场景可关 JIT 裁剪（轻量系统 ace_engine_lite 走纯解释路线）。

## 7. 本篇结论

1. ArkCompiler = 前端（es2panda）+ 字节码基础设施（runtime_core/Panda）+ 运行时（ets_runtime）三段式；`.abc` 是贯穿全链路的产物；
2. 执行引擎三级形态（解释/JIT/PGO AOT），AOT 由**系统编译服务**托管（`compiler_service` + `bm compile`），系统框架应用有 AOT 白名单；
3. 运行时以进程内嵌 VM 形态存在（appspawn 体系），并带热修复（quick_fix）、跨 VM、内嵌引擎（jsvm）等平台化能力；
4. 仓颉 = 静态编译的第二条语言路线，6.x 首次开放 API（22 Kit），通过 interop 与 ArkTS 共存混合开发。
