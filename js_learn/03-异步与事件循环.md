# 03 · 异步与事件循环：换一个世界观

> 配对练习：`03-async/` 五题。**本章是整个 JS 学习的重中之重**——不是"新语法"，而是与多线程完全不同的并发世界观。

## 1. 为什么单线程也能"并发"

C 的思路：`read()` 会阻塞 → 想同时干活就开线程 + 锁。

JS 的思路：**一切 IO 都不等待**。发起请求立刻返回，事件发生了再回来处理。单线程意味着：

- 当前代码跑完之前，**任何事件都插不进来**（没有抢占，不需要锁，没有竞态）
- "并发" = 把等待时间让给别人用
- 代价：**绝不能写死循环/长计算**（会把所有人的事件都卡死）

```
线程模型（C）：  你等人搬砖的同时你可以搬别的砖（但砖会互相踩，要加锁）
事件循环（JS）：工地只有一个你，但搬砖的指令会排队，等砖的时间你一直在处理别的指令
```

## 2. 事件循环模型（默背版）

```
┌─────────────────────────────────────────┐
│ ① 调用栈：同步代码一口气跑完              │
└──────────────────┬──────────────────────┘
                   ↓
     ② 微任务队列：清空【全部】
        （Promise.then 的回调、await 的续体）
                   ↓
     ③ 宏任务：只取【一个】（如某个 setTimeout 回调）
                   ↓
     回到 ② 清空微任务 → 再取下一个宏任务 ……
```

一句话：**微任务永远插队到下一个宏任务前面。**

验证一下（这就是练习 11）：

```js
console.log('1 同步');
setTimeout(() => console.log('4 定时器'), 0);      // 宏任务
Promise.resolve().then(() => console.log('3 微任务')); // 微任务
console.log('2 同步');
// 输出：1 → 2 → 3 → 4
```

`setTimeout(fn, 0)` 的 `0` 不是 0ms，是"至少等当前同步代码 + 微任务全部清空"。

补充两点（知道即可）：

- `await xxx` 的后续代码 = 微任务（挂起函数，控制权交回事件循环，好了再继续）
- Node 有个 `process.nextTick`，优先级比微任务还高，Node 专属，日常少用

## 3. 回调 → Promise → async/await 的演化史

### 史前时代：回调（认识即可）

```js
getUser(1, (err, user) => {
  getOrders(user, (err, orders) => {   // 嵌套地狱……
    getItems(orders, (err, items) => {
    });
  });
});
```

### Promise：未来值

**Promise = 一个装着"未来值"的盒子**，状态机：`pending → fulfilled(值)` 或 `pending → rejected(原因)`，一旦定格不可逆。

对照 `std::future`：

```cpp
std::future<int> f = std::async(std::launch::async, task);
int v = f.get();     // 阻塞当前线程直到结果就绪
```

```js
const p = fetch(url);   // 立刻返回"未来值"，不等待
const v = await p;      // await：把未来值变成"现在的值"
```

**关键区别：`f.get()` 阻塞线程；`await` 不阻塞任何线程**——它把当前函数挂起、控制权交回事件循环，结果好了再从暂停处继续。这就是"单线程并发"的实现机制。

链式调用（`then` 返回**新的** Promise，所以能链）：

```js
fetch(url)                 // Promise<Response>
  .then(res => res.json()) // Promise<对象>，res.json() 也是异步！
  .then(data => data.items)
  .catch(err => { /* 链上任何一步失败都会到这 */ });
```

### async/await：Promise 的语法糖（现代标准写法）

```js
async function load(url) {
  try {
    const res = await fetch(url);
    if (!res.ok) throw new Error('HTTP ' + res.status);  // fetch 对 404 不抛错，要自己查
    return await res.json();
  } catch (e) {
    console.error('加载失败:', e.message);
    throw e;                    // 想让上层也看见就重新抛出
  }
}
```

五条铁律：

1. `async` 函数**永远返回 Promise**（`return 1` 实际返回 `Promise{1}`；`throw` 变成 rejected Promise）
2. `await` 一个 rejected Promise 会**抛异常**——用 `try/catch` 接
3. `await` 只能写在 `async` 函数里（ESM 顶级 await 是例外，先不管）
4. `await a; await b;` 是**串行**——互不依赖的操作必须并发（下一节）
5. 没 `catch` 的 rejection = **进程崩溃**（`unhandledRejection`）。练习 13 里那行兜底注释就是这件事——这也是调试时"好好的程序突然退出"的头号原因

## 4. 并发：Promise 组合器

| API | 行为 |
|---|---|
| `Promise.all` | 全成才成、一坏全坏；结果**保持输入顺序** |
| `Promise.allSettled` | 全部等完，各自报告 `{status, value/reason}` |
| `Promise.race` | 第一个 settle 的赢（无论成败）——做超时控制 |
| `Promise.any` | 第一个**成功**的赢 |

最重要的对比（练习 14/15 亲手验证）：

```js
// 串行：总耗时 = 150 + 120 + 130 = 400ms
const a = await fetchA();
const b = await fetchB();
const c = await fetchC();

// 并发：总耗时 = max(150, 120, 130) = 150ms
const [a, b, c] = await Promise.all([fetchA(), fetchB(), fetchC()]);
```

为什么并发版有效：`Promise.all([...])` 的数组里**先创建了全部 Promise**（每个创建时就已发起请求），`all` 只是等它们齐。而串行版第一个 `await` 执行完才会发起第二个请求。

**手写 `Promise.all`**（练习 13）是高频面试题，要点：

1. 结果数组**按输入下标**写入（不是 `push`——先完成的可能不是第一个）
2. 计数器：每成功一个 +1，等于总数时才 `resolve`（保持顺序的关键）
3. 任一失败：直接 `reject`（后续成功的结果直接作废）
4. 边界：空数组立即 `resolve([])`

## 5. 宏任务家族（用时再查，认个脸）

- `setTimeout(fn, ms)` / `setInterval(fn, ms)`：宏任务，别忘了 `clearInterval`（第一章的泄漏源头）
- `setImmediate`（Node）：当前轮次结束后尽快执行
- IO 回调（文件、网络）：本质都是"事件发生 → 回调进队列"

## 7. 自测（答案在下方）

1. 微任务和宏任务的核心区别一句话？
2. `await` 和 `std::future::get()` 的本质区别？
3. `Promise.all` 为什么要用下标写结果而不是 `push`？
4. `async` 函数里 `throw` 的异常去哪了？

<details>
<summary>答案</summary>

1. 每轮只执行一个宏任务，但微任务每次都会被**清空**——微任务永远插队到下一个宏任务前面。
2. `get()` 阻塞线程；`await` 挂起函数、把线程让回事件循环，无阻塞。
3. 并发完成的顺序不确定，`push` 会把先完成的排前面；只有按下标写入才能保持输入顺序。
4. 变成函数返回的 Promise 的 rejection；调用方要么 `await + try/catch`，要么 `.catch`，否则 unhandled rejection → 进程崩溃。
</details>
